6. Finding: block edits are not equal to a re-parse (the five block lines of
   section 5 DIFFER), because pkg::style keeps the style attribute and
   presentational hint records of a rule store by element position, once, at
   load (RuleStore.attributes and .hints, AttributeStyle.element). An insertion
   shifts the positions after it, so the records stay with the old positions.

   What follows from it. The round trip of section 3 still holds for block
   (the X inverse restores the positions), and the edit mode's block dump is
   the from-scratch dump of a document whose style records are stale, so it
   cannot be the oracle for a block edit until the records follow the
   elements. This is the position-for-identity problem Q67 names for
   StyleRef.element, in the rule store: a record keyed by NodeId, or an
   operation that records again after a structural edit, removes it; the
   store's record fields are private to pkg::style and the sheets' suffix
   mapping that fills the store is private to pkg::oracle::page, so the
   driver cannot rebuild the store without duplicating load_page, and
   calling add_style_attributes again would append second records.

7. Other notes
   - The module pkg::oracle::layout has no graph edge to
     pkg::base::static_atoms, so the class edits intern the name class
     through pkg::base::atom (it returns the static atom).
   - The driver opens script paths through read_argument_file, which takes
     only relative paths without symbolic links; the scripts are written to
     build/x5/scripts.
   - An edit appends to the document's text storage and a detached subtree
     stays in the arenas, so a script's later edits see a larger document
     than the page; a B edit creates two nodes (the p and its Text), which is
     how edits.py predicts the identifiers an X inverse names (the N line of
     the nodes listing is the arena size).
