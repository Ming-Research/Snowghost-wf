# W4 — dense paragraph preparation

HYPOTHETICAL: C1/C2. The `Census` is a dense **unordered** array of live paragraph
keys in a backing Array with a separate initialized logical count; order is
irrelevant to preparation. Its inverse lives in paragraph metadata. A single
deletion swaps out one key; batches use the disjoint hole/tail algorithm in
design.md. The loop visits that live prefix, not tombstone high-water slots.

Source lines: 33. Original: `prepare_context` in
`renderer/layout/prep.wf`, 25 lines in a 726-line file; the expensive leaf work
is `prepare_paragraph` and text/shaping callees. This rewrite mainly exposes
persistent membership facts, not an already missing paragraph-level parallelism.

```wf
      }
      Child(..) => {

    }

fn append_piece(pieces: &Store<Piece>, piece: Piece) -> result: Result<Key, StorageError> writes(pieces) {
  let space = propagate reserve::<Piece>(store: pieces, count: 1_u64);
  let key = reservation_key(space: &space, at: 0_u64);
  emplace::<Piece>(store: pieces, space: &space, key: key, value: piece);
  return Ok<Key, StorageError>(value: key);
}
```

`prepare_paragraph` is the ordinary text library leaf: it reads its immutable
input and font data, writes its own metrics/text/runs/pieces, and returns Bool
for success. Its source analogue is the existing function in prep.wf, with
piece emission routed through the `append_piece` implementation shown here.
Its effect row is exactly `reads(input), reads(fonts), writes(paragraph)`;
`paragraph_preparation(done, paragraph, input)` is its success-sensitive
postcondition: True means the output metrics/pieces correspond to that exact
immutable input; False promises initialized storage and preserved structure,
not prepared metrics. `preparation_result(ok, scene)` exports that the conjunction
being True makes every census paragraph ready. Its library proof uses complete
census coverage and the True identity/and step of the Bool reduction; readiness
is not inferred merely from the function's name. In this model Child tokens carry
already prepared child-context summaries, so success establishes
`prepared_inputs(part, scene)` for every TreePart. A production caller must also
prepare independent child contexts before making that same readiness claim.
There is no interning table, mutable shaping cache or shared free list is smuggled in.
The streaming text/cluster state, where used by that algorithm, belongs to this
paragraph. A production port retains its existing text failure behavior.

The Census proves both key injectivity and that each key selects Paragraph, so
the other match arms are unreachable under the requirement; they do not silently
skip malformed data. `scene_valid` suspends no cross-table fact when this helper
changes the inside of a paragraph body: back-link, live header, body tag and
census position are outside the helper's writable Paragraph subobject.

Iteration `i` owns the complete reachable paragraph object, including its
`Store<Piece>`, metadata and pages. C2 growth affects only that object's page
directory; ownership separates it from iteration `j`. The `band` accumulator is
one of PAR-2's admitted reductions. There is no early return/propagate in the
counted body. The helper's Result handling, where relevant, finishes inside the
helper, and only a Bool crosses this loop.

`append_piece` is sequential within one streaming producer because the next
piece identity depends on that producer's append state. It creates no dependency
between paragraphs. This is not a promise to serialize all text algorithms:
independent shaping runs can reserve separate ranges when their output counts
are known. The runtime allocator may still contend; source independence is not
an allocator-speed claim. Very short paragraphs can still use one page each,
so P6's small-allocation problem is reduced only where pages amortize multiple
pieces or allocations. See F3.
