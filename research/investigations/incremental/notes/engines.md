## 0. Thesis and vocabulary

### 0.1 What "incrementality decided by data dependencies" would mean precisely

Every stage output is a function `out = f(key)`, where `key` is the explicit set of inputs the function read. An edit changes some inputs. A result is recomputed iff its key changed, and the change stops propagating at the first output that comes out equal ("early cutoff", as in Salsa / Adapton / Bazel). Nothing is hand-placed: no "boundary", no "layer", no dirty flag that a human decides to set. Snowghost already records this as a decision [SG design/pipeline.md]: "each stage ... is a pure Whitefoot function of explicit inputs whose result is memoized by those inputs, because the compiler then proves the memoization key complete and a result that read anything outside its key does not compile".

Implementing that ideal needs four separable mechanisms. Engines differ in how well each is done, and almost every shortfall below is a shortfall in exactly one of them:

1. **Key completeness**: does the key contain everything the function read (otherwise stale output) and nothing it did not (otherwise needless misses)?
2. **Key granularity**: how finely is the input split? A key "the whole ComputedStyle of this element" misses whenever any property changes even if this consumer reads one.
3. **Dirty discovery**: how do you find which results to re-check without visiting the whole graph? Push (mark dependents dirty on write, usually ancestor chains and bit flags) or pull (re-derive keys from the root and compare). Pull costs O(visited), push costs O(marked) plus a walk back down the marked spine.
4. **Output representation**: even when 99 percent of children hit the cache, does assembling the parent's output still cost O(children)? (flat display list, flat offsets, flat vector of paint chunks.) A cache hit that must still be copied/placed/compared is a linear tax per level.

### 0.2 Classification used per mechanism

- **DD-exact**: result keyed by explicit inputs; invalidation falls out of key inequality. (LayoutNG constraint-space cache, WebRender tile dependency lists, Compose skipping, React Compiler memo slots.)
- **DD-approx**: invalidation derived by a static analysis of the dependency structure that over-approximates (Blink invalidation sets, Stylo invalidation maps, `:has()` flags, `ComputedStyle::Diff` hand tables).
- **HP-boundary**: a human or heuristic places a boundary that bounds the damage (`contain`, `content-visibility`, `will-change`, Flutter `RepaintBoundary`, WebRender slices, Unity Canvas, Slate volatile).
- **DIRTY-BIT**: conservative flags set by a mutator and propagated along a fixed structure (ancestor chains), cleared by a lifecycle pass. Correctness depends on the mutator setting them right, not on the data.
- **HEUR**: policy choices that are not about correctness (layerization merging, tile size, when to stop caching a tile).

### 0.3 Headline findings (details in the tree below)

1. **The best of Blink's layout caching already is the owner's ideal**, done by convention in C++: `LayoutResult` is cached under its input `ConstraintSpace`, fragments are immutable and position-free ("clones fragments without offsets", [F layout_ng.md]), and the doc forbids reading outside the key ("layouts should not access any information outside this set, as this breaks caching" [F]). Snowghost Q55 (fragments relative to their formatting context) and `pipeline.md`'s memoization decision are the same move, with the compiler enforcing what Blink enforces by review and DCHECK. What stays hand-placed in Blink is everything around that cache: the `NeedsLayout`/`ChildNeedsLayout` bit propagation, the exclusion of fragmented content from the cache [F, possibly outdated], the relayout-root/containment boundaries, the lifecycle barriers between stages, and the key *coarsening* rules (see 2.1.3) that are hand-written equivalents of "this input did not matter".
2. **Style invalidation is a static dependency analysis over selectors**, not a heuristic (invalidation sets in Blink, invalidation map + ElementSnapshot + restyle hints in Stylo). It is DD-approx: sound by construction, over-approximate by design (descendant/sibling combinators widen to subtrees, `:has()` marks "some elements incorrectly" [F Igalia]). Its output feeds a *hand-written* classification (property -> "affects layout / paint / composite") that is DIRTY-BIT, and that classification throws away per-property information.
3. **Everything downstream of layout in Blink and Gecko is coarser and more hand-placed than layout**: paint chunks keyed by property-tree state, layerization by area heuristics, cc tiles as the unit of raster invalidation, damage as a union rectangle per surface. WebRender is the exception worth studying: per-tile dependency lists (primitives, clips, transforms, image keys, opacity bindings) are DD-exact *inside* a spatial partition that is itself a hand-placed hack.
4. **No mainstream engine pipelines edits across stage boundaries.** Blink runs style, layout, pre-paint, paint on the main thread behind a `DocumentLifecycle` barrier and commits to the compositor behind another; Gecko hands a display list to WebRender's scene-builder thread, which is pipeline-parallel (stage per thread), not dependency-parallel. Stylo is the only part with fine-grained data parallelism (work-stealing over DOM subtrees) and it is bounded by parent-before-child [F Hacks article snippet via search; M].
5. **UI toolkits come closest on the *read-site* idea**: Jetpack Compose invalidates the phase in which state was read (composition vs layout vs draw), Masonry separates "layout sets size" from "compose sets position", Flutter derives relayout boundaries from a declared `parentUsesSize`. These are dependency-determined at call-site granularity with a few hand-placed leftovers (repaint boundaries, stability annotations).
6. **Immediate-mode GPU redraw is a legitimate control, not a strawman**, and WebRender itself began there (Servo's original thesis) and later added picture caching because bandwidth/power on integrated GPUs and mobile mattered [M; the 2018-2020 newsletters show the picture-caching work, F search results]. That is the best evidence that "redraw all, no tracking" has a ceiling, but the ceiling is power/bandwidth, not frame time, on desktop.

## 1. STYLE

### 1.1 Blink: invalidation sets, sibling invalidation, StyleRecalc roots   -- status: established

- **Tracked**: for every rule's selector, per-feature *invalidation sets* (class/id/attribute/tag/pseudo-state names an element must have or lose to matter), with a scope: self, descendants (possibly only those with certain classes), "whole subtree", and later-siblings (+/~ combinators; separate sibling-invalidation design doc, "operates forward along the sibling chain") [F style-invalidation.md summary via search: "the invalidation sets approach ... examining the changed element itself, its descendants, and next siblings, based on the relationship defined by CSS combinators"]. Invalidation sets act as a "mutation filter": most DOM mutations hit no set and trigger nothing.
- **Granularity**: per feature name (a class, an attribute) on a per-element mutation. Output is a set of elements to restyle, with a `StyleChangeType` (local, subtree, reattach).
- **Trigger**: DOM mutation (class/attr/id change, insertion, state like :hover), stylesheet insertion/removal (stylesheet changes use a coarser path: rule-set diff, falling back to "recalc everything" when it cannot reason).
- **Cached**: the invalidation sets themselves (rebuilt incrementally when stylesheets change); `ComputedStyle` per element; the **matched properties cache** and **style sharing** (share a ComputedStyle among siblings/cousins with identical matched rules and identical parent style) [M]. `ChildNeedsStyleRecalc` bits on ancestors let the walk start at a **style recalc root** (the lowest common ancestor of dirty elements, maintained incrementally) instead of the document root [M: `StyleRecalcRoot`].
- **Pathologies**: universal and attribute selectors, `:not()`, deep descendant combinators widen to whole subtrees; `:has()` needs ancestor traversal, so Blink adds mutation filters and two flags (AffectedBySubjectHas, AncestorsAffectedByHas) to avoid it, and the author states the result "is not perfect" with "some elements incorrectly marked for recalculation" [F https://blogs.igalia.com/blee/posts/2023/05/31/how-blink-invalidates-styles-when-has-in-use.html]. Stylesheet mutation bails to "dirty the whole document" in many cases (a Stylo bug title, "tweak style sheet invalidations to bail out to dirtying the whole document less", bugzilla 1407522, [F search result]).
- **Class**: DD-approx. This is the one place where engines literally do static dependency analysis, and it works because the dependency relation (selector grammar) is declarative and finite.
- **Transfer to Snowghost**: the technique transfers directly; the *specific tables* are workaround for a single-threaded pull model where checking an element costs a walk. In Snowghost, where `match` is a function of (element features, ancestor chain features, sibling features, rule set), the equivalent is **a reverse index from feature -> rules -> affected relation (self / descendants / later siblings)** and then a parallel counted loop over the affected set. Same asymptotics, but expressible as ordinary data (a table) rather than as C++ flags. [S] The invalidation set is exactly the "reads" row of `match`, computed per rule rather than declared per function.

### 1.2 Stylo/Gecko: restyle hints, ElementSnapshot, invalidation map, rule tree, parallel traversal   -- status: established

- **Tracked**: an `ElementSnapshot` of the element's *old* state and attributes taken before mutation, so that invalidation can match selectors against both old and new (is a selector's truth value different?) [M]. The **invalidation map** (dependencies by class/id/attr/state, each with a kind: self, parent, ancestor, sibling, later sibling...) says which neighbors may flip; it is "not ordering-dependent" so stylesheet addition can add to it incrementally [F bugzilla/hacks search results]. Restyle hints are bitflags: restyle self (rematch), restyle descendants, restyle later siblings, recascade self, recascade descendants [M]. Hints live in lazily allocated `RestyleData` on elements [F search result].
- **Granularity**: element. RECASCADE vs RESTYLE is a nice split: *rematch* (selector matching, expensive) versus *recascade* (reapply cascade to the same matched rules, e.g. inherited property changed). The **rule tree** (shared cascade results as a trie of rule nodes) makes recascade cheap and structural sharing key-based [M].
- **Cached**: rule tree, style sharing cache, Bloom filter of ancestor features for selector rejection, ComputedValues split into ~two dozen *style structs* each held in an `Arc` shared with the parent when unchanged (inherited structs) [M]. Pointer equality on a struct is the change test, so granularity is per struct group, not per property.
- **Trigger**: DOM mutation, state change, stylesheet change, animation tick, and (through hints) a parent's computed-value change.
- **Parallel**: work-stealing over the DOM; when a node is processed its children are split into work units and queued in a rayon pool [F hacks.mozilla.org Quantum CSS result via search]. Bounded by: a child's style needs the parent's computed style first, so depth is a true critical path; sibling-count is data parallel.
- **Pathologies**: stylesheet changes (facebook.com "lots of time spent refreshing the stylist", bugzilla 1386045 [F title]); `eRestyle_Subtree` was the fallback for descendant-combinator changes until refined (bugzilla 1368240 [F title]); pre-Stylo Gecko's restyle was serial.
- **Class**: DD-approx for matching; per-struct pointer-equality early cutoff is DD-exact at struct granularity.
- **Transfer**: (a) *struct-group granularity of the key* transfers directly and is the cleanest idea here: Snowghost should split computed style into consumer-shaped groups so that layout's key contains only layout-relevant groups, paint's contains only paint groups. This is what `ComputedStyle::Diff` in Blink does by hand-written tables [M], and what Q56-style "key = only what this stage reads" does by construction. (b) The snapshot idea (compare old and new) is needed whenever invalidation is *push*; in a persistent-data design where the old tree still exists as a value, the snapshot is the previous version, free. [S] (c) Rule tree = hash-consing of cascade results; transfers if cascade is memoized by (matched rule set, parent computed values), see 1.4.

### 1.3 Style-diff -> change hint: the hand-written bridge between stages   -- status: established, hand-placed

- Blink: after recomputing an element's `ComputedStyle`, `ComputedStyle::StyleDifference` (a field-wise diff, [M]) yields a small set of reasons: needs layout, needs paint invalidation, needs recomposite, needs reattach. Gecko: `nsChangeHint` bitset (reflow, repaint-frame, update-overflow, reconstruct-frame, update-transform, ...) from `nsStyleStruct::CalcDifference`. Servo: `RestyleDamage` (repaint, reflow-out-of-flow, reflow, rebuild-flow) and in the new layout `LayoutDamage` with box damage vs "empty" damage meaning only fragment layout [F https://github.com/servo/servo/pull/37957].
- **Tracked/granularity**: per element, per *class of consumer*, never per property or per consumer function.
- **Pathology**: "any layout-affecting property changed => this element's layout is dirty" even when the layout algorithm reads only a few of the layout-affecting fields, and when *the same layout inputs came out equal after the change* (e.g. `width: 50%` -> `width: 400px` on a 800px parent). This is why a layout engine can still do work whose result is bit-identical; early cutoff must happen again at the layout result boundary (2.1).
- **Class**: DIRTY-BIT with the classification hand-maintained per property (in Blink generated from property field groups [M], but the *meaning* "this property affects layout" is asserted by humans).
- **Transfer**: this entire layer is a workaround for not having per-consumer keys. In Snowghost, style produces groups (1.2) and each consumer function's key is its own groups; there is no change hint to maintain. What replaces it: an obligation that every consumer's declared reads are group-granular (compiler checks reads vs declared key). [S] Risk: group boundaries are a design choice with a tradeoff (finer groups = more key-compare cost per node), see experiment E1.

### 1.4 Computed-value memoization (style sharing, matched properties cache)   -- status: established, heuristic key conditions

- Blink's **style sharing**/**MPC** key: matched declaration sets + parent style (+ some flags). Sharing between siblings requires a hand-written list of conditions (same tag, same classes, same attribute presence, no `:hover`-style state, no sibling combinators affecting it, parent sharing, ...) because the "key" the algorithm should use (everything match read) is not available as data [M]. Gecko/Stylo has the same shape (`StyleSharingCache`, a long hand-written list of candidate checks, [M]).
- **Class**: HEUR over a dependency question. The key is an approximation chosen so that equal keys imply equal outputs; misses are common.
- **Transfer**: in Snowghost, if `match` and `cascade` are explicit-input functions the sharing condition is derived rather than listed: identical (matched-rule-set id, parent computed id) => identical output, by hash-consing. [S] That requires interning rule sets and computed-value structs; the pure-function decision already points here. Caveat from the Snowghost layout record: shared caches across independent units create ordering between them (Q47/Q53 refuse a shared shaping cache for this reason [SG]); hash-consing is the "lock-free interning problem" and either needs a concurrent interner (not provable-independent), a two-phase "collect keys in parallel, intern sequentially, then use" pattern, or accepting duplicates.

### 1.5 Cross-cutting style pathologies   -- status: hard, real

- **Document-order dependencies**: counters/quotes (Snowghost Q52), `:nth-child` and sibling combinators (a later-sibling chain), `:first-child` style structural pseudo-classes. Inserting one node at the start of a 10k-sibling list invalidates structural pseudo-classes of all later siblings in the worst case. Engines handle by: sibling invalidation sets (Blink), RESTYLE_LATER_SIBLINGS (Stylo), and per-parent "child index" caches [M]. This is an inherent data dependency; the engine's only freedom is to make the check O(1) per sibling and not re-run selector matching for siblings whose relevant structural fact did not change. [S]
- **Inheritance chain**: any inherited-property change under a node forces recascade of the whole subtree *unless* the child's matched rules do not set the property and the parent's inherited struct is pointer-equal. This is key-based early cutoff done in one place (struct sharing).
- **Environment inputs** (viewport size for media queries/vw units, font metrics for `em`/`ex`, `container queries`): treat as explicit inputs. Container queries make style depend on layout (size) results: a **cycle between stages**, which Blink resolves by running style *during* layout for the container's subtree (a layout-containment-required design) [M]. Any end-to-end incremental pipeline must have an answer to this stage-feedback edge; engines' answer is restricting it (`container-type` implies containment). That is a hand-placed boundary placed *by the language* to keep the dependency graph acyclic. Worth noting for the design: the dependency graph is not a DAG across stages in CSS.

## 2. LAYOUT

### 2.1 Blink LayoutNG   -- status: established; the closest existing system to the ideal

#### 2.1.1 Layout result cache keyed by ConstraintSpace

- **Tracked**: every `LayoutResult` (immutable `PhysicalFragment` tree plus metadata) stored on the layout object with the `ConstraintSpace` it was computed under; "The system stores both the input constraint space and resulting fragment on the LayoutBlockFlow object" and reuse needs identical constraint space (via `operator==`), no break token, and not `NeedsLayout()` [F https://chromium.googlesource.com/chromium/src/+/main/third_party/blink/renderer/core/layout/layout_ng.md]. NB: that page reads as an early-LayoutNG-era document; the "only without break tokens" limitation may be since relaxed; check before quoting.
- **Granularity**: per layout object (per box/formatting-context entry). Key is (style, constraint space (available size, percentage resolution sizes, fixed-size flags, BFC offset, margin strut, exclusion space/floats, fragmentation info, `is_new_formatting_context`, ...)).
- **Trigger**: a miss when any key component differs or the object's own `NeedsLayout` bit is set (set by style/DOM change).
- **Cached**: the whole fragment subtree below the box, wholesale. A hit skips the entire subtree.
- **Immutability + relative positions**: "each fragment becomes immutable and is never changed again", "no upward parent references and no data bubbling down the tree" [F https://developer.chrome.com/docs/chromium/renderingng-data-structures]. Offsets are the parent's business; "the system intentionally clones fragments without offsets" [F]. So a moved subtree is reused without touching it. This is Snowghost Q55 [SG].
- **Class**: DD-exact in design, convention-enforced in code: "layouts should not access any information outside this set" [F]. Violations cause stale or non-deterministic layouts and are a recurring bug class [M].
- **Pathologies / limits**:
  - *Key too fine, so misses*: BFC-relative inputs (exclusion space, margin strut, BFC block-offset) are in the key because later siblings really depend on earlier floats, so any change that moves a float changes keys for subsequent siblings in that BFC even if they do not collide with it [M]. Engines mitigate via the coarsening in 2.1.3.
  - *Key not coarse enough*: inline-size changes miss all text descendants, because line breaks truly depend on width. Sometimes breaks are identical across a range of widths; engines only exploit that for the one-line case (see 2.1.3, [M, low confidence]).
  - *Only the box's result is cached, not partial progress*: a changed child recomputes its **parent's whole algorithm** (the parent block loop re-runs, children hit cache). Cost O(children) per level on the dirty spine (the "wide parent" tax, see 2.4).
  - *Fragmented content* (multicol, print): break tokens thread state between fragments so results are not independently cacheable [F, maybe outdated].
  - *Multi-pass algorithms* (flex, grid, table) measure children several times under different constraints; Blink stores separate cache slots (measure vs layout) [M, moderate confidence].
  - *Inline formatting*: the `InlineItems`/shaping data for an inline formatting context are rebuilt per IFC when its text or style changes; shaping results are cached in a **word-level shape cache shared across the document** keyed by (font, text) [M]. That is a shared cache of exactly the kind Snowghost Q53 refuses (because it orders independent paragraphs [SG]); the engine accepts it because single-thread main-thread layout has no ordering problem.
- **What Blink does that Snowghost must decide**: Blink keeps results *on the mutable layout object*; identity of the layout object is the cache's address. The "node identity -> latest result" map is a mutable side table, and `NeedsLayout` flags are the version stamps. A persistent-value design replaces the mutable table by (a) keyed lookup of previous result by node id, or (b) hash-consed results keyed by input.
- **Needs from Whitefoot**: an immutable arena/tree of results addressable by stable node id; equality/hash on constraint-space struct; the compiler-proved "result read only key". 
- **Experiment**: E1 (key-hit simulation) below measures what fraction of boxes would hit a (style groups, constraint space) key after typical edits on the three pages, using the existing full-recompute drivers only.

#### 2.1.2 Dirty propagation, layout roots, relayout boundaries, containment

- **Tracked**: `NeedsLayout` on the changed object, `ChildNeedsLayout` on ancestors, up to a **layout root**: the nearest ancestor that cannot be affected by the change (historically "relayout boundary": fixed-size box with overflow clip, etc.; in NG, out-of-flow positioned objects and `contain: layout size`/ `strict` roots are subtree roots) [M]. Layout then starts from the roots instead of the document root; if a root's size does not change, its ancestors need nothing. If it does, `MarkContainerChainForLayout` marks the chain [M].
- **Containment** (`contain: layout|paint|size|style|strict|content`) and `content-visibility: auto|hidden`: the author promises a subtree's layout/paint is independent of the outside (and vice versa) and the engine skips outward dependencies; `content-visibility: auto` additionally skips layout/paint of subtrees not near the viewport, using `contain-intrinsic-size` as a placeholder [M: shipped Chrome 85].
- **Granularity**: subtree. **Cached**: nothing new; it prunes the walk and the dirty propagation. **Trigger**: promise by author.
- **Pathologies**: (1) *the boundary changes semantics*: layout containment makes the box an independent formatting context and the containing block for absolute/fixed descendants, stops margin collapsing through it, clips ink overflow under paint containment; size containment hides intrinsic size. So the promise is a language feature with visible effects, not a free optimization. (2) Authors place it by guess and measure; no tool says where it would be *sound*. (3) `content-visibility: auto` trades *exactness* for speed: the scroll height and anchors for skipped subtrees are estimates, hence scroll jumps unless `contain-intrinsic-size` is accurate [M].
- **Class**: HP-boundary, author-driven. Notably, the *engine could derive the same boundary automatically in the cases where it is sound* (fixed definite size + overflow clip, or any box whose content layout read only its own width and whose width did not change, which is what the constraint-space key finds dynamically). Containment is how authors tell the engine what the dependency analysis cannot see.
- **Transfer**: the *semantic* effect of containment is what Snowghost gets automatically if independent formatting contexts are keyed by (available size, style) alone (Q55: "a context's inside then depends on its available size alone, so sibling contexts lay out independently and moving a context touches none of its contents" [SG]). Snowghost then does not need `contain: layout` for incrementality, only for the *dependence-cutting semantics* that CSS authors expect. `content-visibility` is a different concern (demand-driven laziness, see 2.5).

#### 2.1.3 Key coarsening, simplified layout, size-only reuse

- **Mechanism** [M, moderate confidence, names approximate]: LayoutNG's cache check is not pure equality. It records on each result flags such as "depends on percentage block size", "has a descendant that depends on percentage block size" and compares only the constraint-space components the result actually consumed; a result can be reused when only the available block size changed but nothing in the subtree resolved against it; and a "simplified layout" path re-runs only out-of-flow positioned children or re-places children without re-running their layout when the box's own size changed in a way children do not read.
- **Why it matters**: this is the engine discovering by hand that **the key should be the *dependencies actually read***, recorded dynamically in the result (the algorithm sets a "read percentage block size" bit when it reads it). That is Salsa/Compose-style dynamic dependency recording, hand-coded for a fixed list of ~a dozen inputs.
- **Class**: DD-exact via dynamic read-recording over a fixed, hand-chosen set of dimensions; plus hand-written reuse rules.
- **Pathology**: every new layout feature must extend the recorded set or the cache is wrong (a bug source) or too conservative (a perf bug). The list lives in the heads of the layout team.
- **Transfer (promising)**: the same idea with **validity predicates instead of equality**: a result stores not "I was computed at available inline size 800" but "I am valid for any available inline size in [a, b)" (for a paragraph: the interval of widths over which line breaks are unchanged; for a block with `width: auto` whose children are all one-liners: [max-content, inf)). Then a resize that stays inside the interval hits without recomputation. The compiler could compute such intervals if layout is written with comparisons against the input (`if w >= lw` => records the threshold), a dynamic-recording scheme, or the author can compute them in the algorithm (line breaker reports the width range it was stable over). This goes beyond what any shipped engine does, to my knowledge (engines handle only the degenerate cases). [S] Experiment E3.

#### 2.1.4 What LayoutNG does not have (the shortfall list)

- No parallelism inside layout (LayoutNG is main-thread, single-threaded; "parallel layout" has been explored in Blink/Servo but is not shipped in Chrome [M]).
- Dirty bits set upward by mutators, walked from roots; whole-tree `NeedsLayout` verification invariants exist in DCHECK builds because stale flags are a bug class [M].
- Lifecycle barrier: style -> layout -> prepaint -> paint -> commit are phases over the *whole document* (`DocumentLifecycle`), forced synchronously by script reads (`offsetWidth`), which interleaves style/layout with JS and prevents any cross-stage pipelining. Not a layout-design problem; a web-API semantics problem that Snowghost inherits if it hosts a DOM API with synchronous layout queries. [S: sync layout queries can be answered from a lazily-demanded region of a persistent result tree; costs and semantic caveats are not studied here.]

### 2.2 Gecko layout: frame tree, reflow, dirty bits   -- status: established, older

- **Tracked**: frames carry `NS_FRAME_IS_DIRTY`, `NS_FRAME_HAS_DIRTY_CHILDREN`; style change hints (`nsChangeHint_NeedReflow`, `ReflowChangesSizeOrPosition`, `ReconstructFrame`, `RepaintFrame`, `UpdateOverflow`, ...) are applied by the RestyleManager to frame dirty bits and enqueue **reflow roots** on the PresShell [M].
- **Reflow**: `ReflowInput` carries available size, percentage bases, and `IsIResize/IsBResize` flags so a frame can skip child reflow when its inline size did not change and its children are not dirty. That is a hand-coded approximation of the constraint-space comparison [M].
- **Frame reconstruction**: a style change of `display` or similar rebuilds a frame subtree rather than patching it ("ReconstructFrame" hint) - the equivalent of Servo's "box damage". Costly: destroys retained layout state.
- **Pathologies**: reflow of a block after `float`/clear changes dirty everything after it in the BFC (`block reflow` with `nsFloatManager` carrying state, similar to NG's exclusion space); text frames re-break on width changes; frame reconstruction is a performance cliff [M].
- **Class**: DIRTY-BIT + hand-coded resize checks. Less cache-based than Blink NG (mutable frames, no immutable results).
- **Transfer**: same lessons as NG, plus: mutable frames with per-frame state is the design Snowghost is *avoiding* by Q55/Q56.

### 2.3 Servo: old parallel layout, layout 2020 incremental attempts   -- status: partially established

- **Old Servo layout (2013 era)**: flow tree with `RestyleDamage` bits from style diff, three passes (bubble inline sizes bottom-up, assign inline sizes top-down, assign block sizes bottom-up), each parallelizable by tree traversal over dirty subtrees; incremental flow tree construction had its own wiki page ("Incremental flow tree construction", [F search result title]) [M for the rest].
- **Layout 2020 / current**: started as full rebuild of box tree and full fragment-tree layout; recently grew real incrementality, with (a) **incremental box tree construction**, "Servo now has its first truly incremental box tree layout, rather than a previous dirty-roots-based approach" [F https://servo.org/blog/2026/03/31/february-in-servo/ and PR #37751 title via search]; (b) `LayoutDamage` that distinguishes *box damage* (children must be recollected/rebuilt, propagated upward during restyle damage propagation) from *empty damage* (only fragment-tree layout needed, so box-tree construction is skipped) [F https://github.com/servo/servo/pull/37957]; (c) boxes for floats and independent formatting contexts and their descendants can be reused depending on damage and "avoid damaging their parents" [F]; (d) **reuse of cached fragments in independent formatting contexts** instead of all-or-nothing fragment layout, with the stated groundwork "a general layout caching mechanism, which requires caching that persists across reflows and algorithms to determine when to invalidate those cached results" [F search summary]; also earlier flex-column caching (PR #34461 title [F]). The post gives no quantified speedups [F].
- **Class**: today DIRTY-BIT/damage-based with an emerging cache keyed on formatting-context inputs; direction of travel is toward LayoutNG's model.
- **Transfer**: Servo's two-level damage (structure vs geometry) matches a natural stage split: *box tree* (depends on DOM + display/position/float style) vs *fragment tree* (depends on box tree + sizes). Snowghost already separates box-tree construction from layout [SG layout DESIGN: "box tree built by one walk followed by one decoding loop"]. A concrete, cheap optimization from Servo's experience: **make box-tree key = the structure-affecting style group only**, so a color or width change never re-runs box construction. Independent formatting contexts are the unit that is both reusable and independent; Snowghost's own measurement says one BFC holds 85-95 percent of text on the three pages [SG pipeline.md "Rejected"], so reuse at BFC granularity is too coarse to help on real pages, and you need caching at *block/paragraph* granularity within a BFC (NG's per-box cache does exactly that, subject to the exclusion-space key).

### 2.4 The "wide parent" and prefix-sum problem   -- status: hard, no shipped fix known to me

- Every engine above recomputes a parent's algorithm when one child changes: block flow places N children in order, each one's offset the sum of previous block sizes plus margins (with margin collapsing, a *non-associative-looking* but in fact composable operation, and floats/clearance, which are order dependent). Change child k's height => children k+1..N move. With relative fragments (NG, Snowghost Q55) the children are not recomputed, but the parent still writes N offsets (or at least re-runs the loop and N cache lookups). A 100k-children list is the stress case (ecma262 and html5 have very large flat-ish bodies [SG]).
- **Options**:
  1. Accept O(N) cheap per dirty parent: loops over N hits at ~tens of ns each. For N=100k that is a few ms single threaded, parallelizable as a scan. [S] Plausibly adequate; measure (E2).
  2. **Prefix-sum structure**: store the children's positions as a monoid-summarized tree (Zed's `SumTree` for its display map and text layers [M]: a B-tree whose nodes cache summaries, so an edit and a position query are O(log N)). Block-axis offset becomes "sum of summaries to the left"; no per-child offset writes at all; moving a child run is O(log N). Margin collapsing needs a monoid on (height, trailing margin, leading margin) which exists in principle; floats and clearance break pure monoid structure [S].
  3. Parallel scan: with `--par`, an exclusive prefix over children's sizes is a work-efficient scan; critical path log N. Still O(N) work.
- **Transfer**: this is a place where Whitefoot's *provable independence* helps (parallel scan with checked disjoint writes) but dependency-determined incrementality requires a persistent monoid-tree to avoid O(N). Hard; defer until E2 shows the linear tax matters.

### 2.5 Demand-driven vs change-driven   -- status: promising framing

- `content-visibility: auto`, lazy lists, virtualized scrollers, and Q56 ("intrinsic sizes on demand" [SG]) are *demand*-driven laziness: compute only what is needed for the visible output. Incremental computation is *change*-driven. They compose: a result needs recomputing iff (a) its key changed **and** (b) someone demands it. Layout of offscreen content is demanded only for scroll extent and anchoring.
- **Honest limit**: exact scroll extent requires exact layout of everything above and below. Engines accept estimation (content-visibility) or full layout (default). A Snowghost option is *exact but lazily maintained*: keep per-subtree height in a summary tree (2.4 option 2), mark offscreen subtrees stale, recompute lazily when scrolled near or when exact height is demanded. [S]

## 3. PAINT, PROPERTY TREES, DISPLAY LISTS

### 3.1 Blink paint invalidation, PaintController, display item caching   -- status: established

- **Tracked**: display items keyed by (display item client = typically a `LayoutObject`, type) [F https://chromium.googlesource.com/chromium/src/+/main/third_party/blink/renderer/platform/graphics/paint/README.md]. `PaintController::UseCachedItemIfPossible()` / `UseCachedSubsequenceIfPossible()` let painters copy previous items/subsequences if the client is not invalidated [F]. "If a layout object has not changed during the paint tree walk, its display items are copied from the previous list" [F renderingng-data-structures].
- **Trigger**: invalidation reasons set during the PrePaint tree walk (style change, geometry change, background, outline, selection...) by comparing old and new visual rects/styles [M]; `NeedsPaintPropertyUpdate` / `DescendantNeedsPaintPropertyUpdate` bits limit the walk.
- **Granularity**: per layout object (client); subsequences per stacking-context-like unit.
- **Cached**: previous `PaintArtifact` (display item list + paint chunk list).
- **Pathologies**: (1) The **display list is a flat ordered vector** and "caching" means *copying* unchanged runs into the new vector, so a no-op frame still pays O(items) plus the PrePaint walk; (2) **identity is object-pointer**; (3) repaint is object-granular: changing one glyph run repaints the whole `LayoutObject`'s items (a whole text fragment/box background); (4) the paint-order dependencies (z-order, stacking contexts, overflow clips) force subsequences to be recorded in painting order, so a change deep inside a stacking context re-records the context.
- **Class**: DD-approx at object granularity with a pointer-identity key and dirty flags (`ShouldDoFullPaintInvalidation`, etc.).
- **Fast paths (hand-placed)**: "Direct paint property updates" (`DirectlyUpdateTransform`) and "Repaint-only updates" [F paint README]: when only a transform or only a paint (not layout) property changed, skip PrePaint/layerization. These are special cases (transform, opacity, scroll offset, clip) where the engine has proven by hand that nothing else can change.
- **Transfer**: the *shape* to copy: paint results keyed by (fragment id, style paint group) and stored as a tree of per-fragment display-list nodes, not as a flat list. The flat-list-with-copy design is the thing the owner calls "patch on patch"; it is a consequence of needing a linear paint order for the raster API. A tree (or persistent rope) of per-fragment paint nodes with stable ids, flattened only at the shell boundary (or never, if the shell traverses it), makes the unchanged path O(log N) (spine only). [S] But paint order (CSS 2.1 Appendix E stacking) interleaves fragments from different subtrees (`z-index` and positioned descendants lift into ancestor stacking contexts), so the order is a *merge* of sub-sequences per stacking context. Stacking-context boundary is a dependency-determined partition: inside a stacking context, order depends only on its descendants. (see 3.2/3.3)

### 3.2 Property trees and paint chunks   -- status: established; geometry part DD, chunking HEUR

- **Tracked**: four trees (transform, clip, effect, scroll); each element has a 4-tuple "property tree state" naming its nearest ancestor node in each [F renderingng-data-structures]. A paint chunk is a run of display items with identical property tree state; "the ordered list of paint chunks ... are the inputs to the layerize step" [F].
- **Why it exists**: "centralizes potentially error-prone geometry and other calculations into one place", making compositing decisions, overlap tests and invalidation possible without walking the DOM; in cc, property tree operations are O(interesting nodes) not O(layers) [F https://chromium.googlesource.com/chromium/src/+/main/docs/how_cc_works.md].
- **Class**: the trees are DD-exact (a visual effect depends on its chain of ancestor effects: transform composition is a pure fold over the chain); "interesting nodes only" is a sparsity optimization. Chunk boundaries are determined by state equality: DD. Layerization (next) is HEUR.
- **Key insight for transfer**: property trees are a *factorization of coupling*: they separate "what is drawn" (display items, local coordinates) from "what space/clip/effect it is drawn in" (property node ids). Scroll, transform animation and opacity change touch only property nodes; no display item changes. That is the thing that makes compositor-only animation incremental at zero repaint, and it is the same factorization as Q55 (fragment relative to context; context offset applied later). [S] Snowghost's display list should keep **local-geometry primitives + a reference to (transform, clip, effect, scroll) nodes**, and the shell resolves them. This is what the Rust shell needs from the format, see section 7.

### 3.3 CompositeAfterPaint and layerization   -- status: established; HEUR

- **Before CAP** (compositing-before-paint): after layout, `PaintLayer` compositing decided which elements get cc layers, then paint recorded into those layers. Layout/paint/compositing were intertwined and compositing reasons were computed from style + geometry (overlap tests) on the layer tree: a long-standing source of bugs and perf cliffs ("squashing", implicit compositing due to overlap). [M]
- **CAP** (shipped around Chrome 94 [M]): paint first, producing chunks with property-tree state, then `PaintArtifactCompositor` *layerizes* the chunk list: merge chunks into cc layers unless they need separate layers (direct compositing reasons: will-change, active transform/opacity animation, scrolling, video/canvas), using overlap and "sparsity/area" cost tradeoffs ("balances GPU memory against rasterization costs" [F renderingng-data-structures]).
- **Granularity/cost**: re-layerization runs when the chunk list or state changed; "repaint-only" and "direct update" paths skip it [F paint README].
- **Pathologies**: layerization is a global-ish pass over the chunk list; heuristics produce over- or under-layerization; `will-change` is an author hack to make a layer appear before the animation starts, trading GPU memory for latency.
- **Class**: HEUR (HP-boundary: will-change).
- **Transfer**: Snowghost's owner position "layering and tiling are hacks" is largely right *as a way to bound the cost of coupled rasterization*. A layer exists because rastering the layer's content is expensive and its transform/opacity changes independently. Both facts can be *measured per property node*: "this transform node changed in last K frames while its subtree's content did not". Layer promotion by observed behavior (like WebRender's tile caching policy, 4.2) instead of author hints. In a Skia-based shell the shell decides; the renderer only needs to export which property nodes are *animated* (it knows: it owns animation descriptions per design/processes.md [SG]).

### 3.4 cc: tiling, raster invalidation, damage in viz   -- status: established, hand-placed partition

- **cc**: layers hold recorded `PaintOpBuffer`s; each layer is split into tiles by `PictureLayerTiling`s at multiple scales; `TileManager` prioritizes visible/near-viewport tiles; raster by worker threads (software) or via GPU raster command buffers; pending vs active tree so the compositor can keep scrolling the active tree while the pending tree rasterizes [F how_cc_works.md]. `SetNeeds*` functions provide "early-out aborts" when nothing changed [F].
- **Raster invalidation**: `RasterInvalidator` compares the previous and current chunk lists, "identifying appearing, disappearing, or reordered chunks"; when only a clip changes "the difference between the old bounds and the new bounds will be raster invalidated", other property changes full-invalidate [F paint README]. The resulting **invalidation region** marks intersecting tiles; a tile re-rasters (possibly partial raster of the dirty rect into the old tile resource, [M]).
- **Damage (viz)**: `DamageTracker` computes per-surface damage (union of invalidated layer rects, moved layers' old and new rects), and the `SurfaceAggregator` aggregates into a damage rect for the frame; the GPU side uses it for scissor/partial swap where the platform supports it [M]. It is typically a *single bounding rect* per surface: two changes at opposite corners produce a nearly full-screen damage. Render passes with no damage can be reused from cache [M].
- **Granularity**: tile (typically 256x256 or by viewport fraction [M]) for content, layer rect for damage, whole texture for compositing.
- **Pathologies**: changing one pixel re-rasters at least its dirty rect within a tile, in practice often a whole tile when raster-inducing changes (scale, subpixel text transform) occur; the commit is a barrier (main thread blocked while layers are copied to the pending tree) [F: "Commit is the process of pushing layer trees and properties from the main thread layer list to the pending tree"]; tile memory and raster-ahead budgets; checkerboarding when raster is behind scroll.
- **Class**: HP-boundary (tile and layer partition) + dependency-exact *within* it (invalidation rect from old/new bounds).
- **Transfer**: tiles exist because (a) the raster surface is a texture with an upload/composition cost per unit and (b) scroll must be served from already-rastered pixels without the main thread. Neither is a CPU-compute constraint; they are constraints of the **shell's** raster/present model. Snowghost's shell is Skia-based [SG processes.md]; tiling decisions are the shell's, and the renderer should not be shaped by them beyond exporting accurate, stable-id damage information (section 7).

### 3.5 Frame dependency across stages: what Blink does at the barriers

- Main-thread frame = BeginMainFrame lifecycle (animate, style, layout, prepaint, paint, layerize) then commit; the compositor thread draws from the active tree meanwhile (scroll, transform and opacity animation, video). So *compositor-only properties are the only genuinely cross-stage-decoupled computation* in Chrome, and they are decoupled by being the properties whose dependency set is tiny and known (they touch only property-tree nodes). The owner's observation ("only changes the compositor handles alone, such as transform and opacity animations, stay fast" [SG pipeline.md]) matches the architecture exactly.

## 4. GECKO / WEBRENDER

### 4.1 Gecko retained display lists and frame-based invalidation   -- status: established, hand-placed

- **Tracked**: `nsDisplayList` built by walking the frame tree; since ~2018 *retained display lists*: `RetainedDisplayListBuilder` keeps the previous list and rebuilds only for **modified frames** (those marked by style hints / invalidation), merging old and new item lists by frame (`MergeDisplayLists`) [M]. Falls back to full rebuild when too much is modified (a fraction threshold) [M, low confidence on exact rule].
- **Granularity**: frame (paintable unit); invalidation by frame property updates and `nsDisplayItem` comparison (`CalculateBounds`/`IsInvalid`/`ComputeInvalidationRegion`) [M].
- **Pathologies**: merge is delicate (z-order and stacking context ordering across old and new); heuristic fallback thresholds; frame-property bookkeeping errors were a recurring source of stale paint [M].
- **Class**: DIRTY-BIT + merge heuristic.
- **Transfer**: documents the cost of repairing a *flat ordered list* with changed members: merge by identity plus fallback. A tree-structured display structure avoids needing the merge. [S]

### 4.2 WebRender: interning, spatial tree, picture caching (tiles)   -- status: established; most transferable raster-side design

- **Pipeline** [M]: content process builds a display list; a **scene builder thread** consumes display lists and builds a scene with *interned* primitives (clips, text runs, images, rectangles etc. get stable handles in per-type data stores; frame-to-frame the same primitive reuses its handle); a **render backend thread** builds frames (`FrameBuilder`: spatial tree resolution, visibility, picture tree, batching); a **renderer** executes GPU draw calls.
- **Interning**: primitives and their "descriptors" are deduplicated by content hash into stable ids; this lets the frame builder detect "nothing about this primitive changed" by id equality, instead of by diff. Design goal stated by the authors: avoid rebuilding from scratch at every frame [M].
- **Spatial tree**: scroll frames, reference frames (transforms), sticky; per-frame it computes world transforms and the relative transform between any node and the picture-cache root; scrolling updates only spatial nodes [M]. Same factorization as property trees (3.2).
- **Picture caching** (tile-based cache of the content of a *slice* of the display list): the main content (and scroll roots) are split into slices, each divided into tiles (default roughly 1024x512 [M], tile sizes tuned for scrollbars [F moz://gfx newsletter 50]). Each tile owns a **dependency list**: the primitives, clips, transforms, image keys, opacity/color bindings that overlap it, with their descriptors. Each frame the new dependency list is compared with the previous; a tile is dirty iff its list differs; dirty tiles re-raster, with a **dirty rect inside the tile** ("multiple dirty rects" and "per-tile valid rect to reduce overdraw" landed 2019-2020 [F search results from moz://gfx newsletters]). Tiles that invalidate on consecutive frames are demoted to uncached (drawn directly) [M, exact policy not verified]. Identical frames are detected and composition skipped ("detect identical frames and skip composition" [F newsletter 50]). Native compositor surfaces for video [F newsletter 50].
- **Class**: DD-exact (dependency list per tile; early cutoff by comparing descriptors) *inside* a hand-placed spatial partition (slice and tile grid) with HEUR (promote/demote policies).
- **Pathologies seen in the wild**: choppy YouTube when tiles invalidated every frame (bugzilla 1559284 [F title]); slow scrolling on weather.com (bugzilla 1689746 [F title]); snapping/rounding errors causing spurious invalidation when zoomed [F newsletter 50]; blur filters needed special invalidation handling [F newsletter 37 search snippet]; "extremely large primitives" in tile dependency lists needed special casing [F search snippet]. Each shows how an approximate key (float-valued geometry, transforms relative to a root, filter bounds) leaks nondeterministic or wide invalidation.
- **Cost**: per-frame work to rebuild and compare tile dependency lists: O(visible primitives); proportional to *visible content*, not document size. Memory: tile textures.
- **What it misses**: still a spatial partition: one changed primitive re-rasters its tile region (the dirty rect shrinks work within the tile but not the dependency comparison cost); correctness of invalidation depends on the *completeness* of the descriptor hash (a missing field = stale pixels; they had bugs of this form, e.g. 1651797 "doesn't draw parts of the charts" [F title]).
- **Transfer (promising, for the display-list format and for shell design)**:
  1. **Interned primitives with stable ids** and per-primitive content hash from the renderer: lets the shell compute damage by id equality in O(changed) rather than diffing pixel lists. The renderer *knows* which primitives it re-emitted because it recomputed the paint result of the fragment; a fragment whose paint result was a cache hit emits "same id, same hash" with no work. [S]
  2. **Spatial/property node ids separate from primitives** (see 3.2).
  3. **Tile = optional shell cache, decided by observed invalidation**, not by the renderer.
- **Experiment**: E4 below (display-list size and damage-from-ids vs full redraw on the Skia shell).

### 4.3 The WebRender history as evidence about immediate-mode redraw   -- status: partly memory, instructive

- Servo/WebRender's founding idea was GPU rendering of the *entire display list every frame* like a game engine; picture caching was added later (landed repeatedly in 2018-2019 per the newsletters [F search results, newsletter 33/37]) because on low-end/integrated GPUs and for power, redrawing everything each frame cost too much, i.e. the ceiling for no-tracking is bandwidth/power and low-end hardware, not 60fps on a discrete GPU [M for the motivation; the newsletters confirm the timeline]. See section 6.

## 5. UI TOOLKITS AND FRAMEWORKS

Each entry gives only the incrementality mechanism. All [M] unless a URL is given.

### 5.1 Flutter

- **Layout**: `RenderObject.markNeedsLayout()` walks up parents until it reaches a **relayout boundary**, adds that boundary to `PipelineOwner._nodesNeedingLayout`; `flushLayout` sorts by depth and lays out dirty boundaries. A node is its own relayout boundary automatically if: parent did not use its size (`parentUsesSize == false`, declared at the call `child.layout(constraints, parentUsesSize: ...)`), or `sizedByParent`, or constraints are tight, or parent is not a RenderObject.
- **Class**: DIRTY-BIT, but the boundary is **derived from a declared data dependency** (`parentUsesSize`). It is the cleanest example of "dependency declared at the call site => boundary falls out". The declaration is by hand (a flag the parent author must set correctly; getting it wrong gives stale layout).
- **Protocol**: box constraints down, sizes up, parent sets position afterward ("constraints go down, sizes go up, parent sets position"): single pass, each child laid out once per parent layout, positions not part of the child's result (same factoring as Q55). Intrinsics are a separate cached API.
- **Paint**: `markNeedsPaint` walks up to the nearest **repaint boundary** (`isRepaintBoundary`, set by `RepaintBoundary` widget and by some widgets like scrollables), each of which owns a compositing layer; a boundary re-records its picture. Hand-placed. Too few boundaries => repaint big areas; too many => layer/memory overhead. The "repaint rainbow" debug overlay exists precisely because placement is by the developer. The engine raster cache caches a picture after repeated use (access-count threshold; heuristic) and uses damage/partial repaint where available [M].
- **Build**: `setState` dirties an Element; `BuildOwner` rebuilds dirty elements in depth order; `Widget` identity (`identical`/const) short-circuits subtrees; `InheritedWidget` dependents are tracked at runtime (`dependOnInheritedWidgetOfExactType`, aspects with `InheritedModel`) = *dynamic* dependency recording.
- **What it misses**: no cross-subtree parallelism (UI isolate single thread); repaint boundary placement manual; rebuild skipping depends on widget identity discipline.
- **Transfer**: (a) *derive the layout boundary from "did parent read my size"*: in Whitefoot the effect row / reads of the parent function makes this static: if the parent's key contains the child's result size only via fields it reads, the dependency is explicit. (b) Setting position outside the child's result. (c) Repaint boundaries: do not copy (workaround for a raster cache model).

### 5.2 Jetpack Compose and SwiftUI   -- fine-grained invalidation, closest to ideal in the view layer

- **Compose**: compiler plugin transforms `@Composable` functions to carry a `$changed` bitmask per parameter and wraps bodies in restartable groups stored in the **slot table** (a gap buffer of groups). A function is **skippable** if all parameters are stable (compiler-inferred) and equal to last call [M: Kotlin 2.0.20 "strong skipping mode" also skips on unstable params using instance equality]. State reads are recorded by the **snapshot system**: reading `State<T>` inside a composable subscribes that **recompose scope** (the nearest restartable function); writing invalidates exactly those scopes. Phases: composition -> layout -> draw; state read inside a layout lambda (`Modifier.offset { }`, `graphicsLayer { }`, `drawBehind {}`) invalidates only that phase, so e.g. scroll offset applied in the draw phase triggers no recomposition and no remeasure [M].
- **Class**: DD-exact at function-call granularity with *dynamic* read recording, plus HEUR/hand parts: stability inference (unstable types silently break skipping; `@Stable/@Immutable` annotations are hand assertions), `remember(keys)`, `derivedStateOf`. Layout side: `LayoutNode` with `needsRemeasure/needsRelayout`, relayout boundaries (`affectsParentSize`) like Flutter. Draw side: `RenderNode`/`GraphicsLayer` retained per layer with parent invalidation [M].
- **Pathologies**: (1) lambdas/unstable params defeat skipping unexpectedly; (2) reading fast-changing state at the wrong phase (e.g. scroll offset read in composition) recomposes every frame; (3) overhead of the slot table and snapshot bookkeeping per call (not free; Compose docs advise not over-granularizing) [M].
- **Transfer (strong)**: the **phase-of-read determines the damage** idea: a state variable's consumers are classified by *where it is read*. For Snowghost: a CSS property's consumers are classified by which stage function reads it (style group -> layout vs paint vs composite). The compiler's static reads-row gives this without runtime recording. The part that does *not* transfer: runtime snapshot subscription (needs tracked reads at runtime; Whitefoot has static effect rows, over-approximate in structure but zero-cost). [S] Open question: whether static row granularity ("reads(style)") is fine enough; it likely must be per-field-group to be useful (E1).
- **SwiftUI** [M, closed source, partly reverse-engineered]: AttributeGraph of memoized attributes with dirty propagation; a view's `body` is skipped if its inputs compare equal (field-wise equality via reflection/POD memcmp, or `Equatable`), `@State` and `@Observable` track reads (Observation framework does per-property read tracking, since iOS 17); layout via proposal protocol ("parent proposes a size, child chooses, parent places") with a `Layout` cache; known pathologies are unexpected extra body evaluations and identity (`.id`) mishaps debugged with `_printChanges`. Same class as Compose.

### 5.3 React Fiber and fine-grained reactivity (Solid, signals, React Compiler)

- **React Fiber**: render phase builds a work-in-progress fiber tree from the current one (double buffering via `alternate`), with **bailout** when props are `Object.is`-equal and no pending update/context change below; priority lanes and time slicing make work interruptible. Cost: reconciliation is O(subtree) from the root of the update, comparing props, unless memoized by hand (`memo`, `useMemo`, `useCallback`). The **React Compiler** automates memoization by computing dependencies of each expression at build time and caching by slot: DD-exact via static analysis, with a hand-written "rules of React" purity assumption; closest analogue of Snowghost's "compiler proves the key complete".
- **Solid / signals / Svelte 5 runes**: no virtual DOM diff; each DOM binding is an effect subscribed to exactly the signals it read (dynamic dependency graph), so an update touches O(changed bindings). Costs: per-binding subscription memory; propagation must be glitch-free (topological ordering), which serializes propagation at shared dependents; no layout concept (the browser does layout).
- **Class**: DD-exact (dynamic recording). **Lesson**: the diff itself is the cost in VDOM designs (O(N) to find changes); push-based fine-grained graphs avoid it at the price of graph maintenance. This is the push vs pull tradeoff (0.1.3).

### 5.4 Xilem / Masonry (Linebender)

- **Xilem**: app-state -> view tree rebuilt, then `View::rebuild(prev_view, ...)` diffed against previous view tree to patch the retained widget tree (Elm/SwiftUI shape); `memoize` and lenses (`lens`/`map_state`) cut diffs.
- **Masonry**: widget tree with explicit **passes**: `update_tree`, `layout`, `compose`, `paint`, accessibility, each pass walking only paths flagged by per-widget bits that merge upward (`needs_layout`, `needs_compose`, `needs_paint`, children-changed...). **layout computes sizes; compose computes transforms/offsets**: moving a widget needs only compose, not layout [M]. Paint produces a `Scene` fragment per widget retained and re-appended; Vello rasterizes the whole scene on the GPU every frame.
- **Class**: DIRTY-BIT flags merged upward (same as Blink bits) but with a clean separation of concerns by pass; no raster caching (GPU compute redraws everything).
- **Transfer**: compose-vs-layout split = Q55. "Retain the encoding, redraw on the GPU" is the hybrid in section 6.

### 5.5 Zed GPUI and the editor display map   -- status: established in practice; exemplary on text

- **GPUI**: hybrid immediate/retained. Every frame the element tree is produced from retained entities by `render`, then `request_layout` (Taffy flexbox/grid) -> `prepaint` -> `paint`, emitting a `Scene` of primitives (quads, shadows, glyph sprites from an atlas, paths) that is drawn by one batched GPU pass (Metal/Blade) [M]. **View caching**: a view marked cached is skipped if it was not notified (`cx.notify()`) and its bounds/style unchanged; the previous frame's recorded ranges of layout, hitboxes and scene primitives are *replayed* (`reuse_prepaint`/`reuse_paint` style APIs) [M, moderate confidence in names].
- **Editor core**: the **display map** is a stack of coordinate transforms (inlays, folds, tabs, soft wraps, blocks) each stored in a **SumTree** (B-tree with per-node summaries); an edit is propagated by applying an `Edit` list through each layer, O(edits x log N), and position conversions are O(log N) [M, high confidence on SumTree and layered maps].
- **Class**: coarse (view-granularity) caching for UI chrome; DD-exact via persistent summary trees for the text.
- **Transfer (strong, for 2.4)**: summary trees *are* the dependency-aware layout structure for long sequences: a child's contribution to the parent is a summary; the parent's offset queries are prefix folds. For Snowghost this answers "block flow over 100k children without O(N) per edit" and "line index to y offset", and parallelizes by splitting the tree.

### 5.6 Makepad

- Retained draw lists with per-view `redraw` requests; instanced SDF shader draw calls; "turtle" layout, a forward single pass with no constraint solving. [M, low confidence; I did not verify the details.] Takeaway: very fast because layout semantics are simple (no intrinsic-size feedback), i.e. cheaper than CSS by restricting the model; not applicable to a CSS renderer.

### 5.7 Unity UGUI/UI Toolkit, Dear ImGui, Unreal Slate (game-engine UIs)

- **Dear ImGui**: immediate mode; rebuilds command lists every frame on the CPU, O(visible widgets); auto-sizing needs a one-frame lag; no retained state beyond ids. Works because UIs are small and drawn by GPU every frame.
- **Unity UGUI**: dirtying at **Canvas** granularity (hand-placed): any dirty element rebuilds the whole canvas's batched mesh; the standard advice is to split canvases by update frequency. **UI Toolkit**: per-element dirty flags (layout/repaint/transform/styles).
- **Unreal Slate**: invalidation panels/boxes cache draw element lists and layout; widgets declare `Volatile` (hand-placed escape hatch for always-changing widgets) and call `Invalidate(reason)` with reasons (layout, paint, volatility, child order, render transform, visibility) [M].
- **Class**: HP-boundary/DIRTY-BIT. They are evidence that when authors must place boundaries, they do so with performance guidelines ("split your canvas"), i.e. the owner's complaint about Chrome applies even to dedicated UI toolkits.

## 6. THE CONTROL CASE: REDRAW EVERYTHING ON THE GPU

- **What it is**: no raster cache, no damage; per frame, upload/encode the display structure and let the GPU draw all visible primitives (WebRender's original design, Dear ImGui, Vello, Pathfinder, game UIs).
- **What it buys**: raster-side incrementality bookkeeping (tile dependency lists, damage unions, raster invalidation, layerization) disappears; per-frame cost = O(visible primitives) CPU encoding (cacheable per fragment) + GPU time ~ pixels x overdraw.
- **Back-of-envelope [S, not measured]**: a 4K frame is ~8.3M pixels; one full-screen write at 4 bytes is ~33 MB; at 120 Hz that is ~4 GB/s of write bandwidth per layer of overdraw, tolerable on discrete/Apple GPUs, noticeable on integrated GPUs and battery. Text-heavy pages have high glyph counts (ecma262 measured at 1.9M characters, html5 2.6M [SG layout DESIGN]) but only viewport glyphs matter: tens of thousands.
- **What it costs**: power (partial present saves energy even when frame time is fine), low-end GPUs, anything with large blur/filters/video compositing (cost scales with pixels), and expensive paths (large blurs, complex clips) that would be cached in a tiled design.
- **Evidence**: WebRender chose to add picture caching after launch (see 4.3); Chrome damage-tracks aggressively for power; Zed and Vello-based Masonry accept full GPU redraw for application UIs.
- **Class**: not an incrementality design at all: moves cost from CPU diffing to GPU bandwidth.
- **Transfer**: the correct comparison for any display-list-diffing scheme is *diffing cost vs full-redraw cost*. If the shell draws the viewport from a retained display tree with cached per-fragment encodings, then the renderer's incrementality duty reduces to "recompute only changed fragments' paint results and report them", and **damage tracking becomes an optional shell optimization for power**, not a correctness or latency requirement. This means Snowghost can postpone damage/tile machinery without foreclosing it, if display-list nodes have stable ids and hashes. [S]

## 7. SYNTHESIS: WHAT TRANSFERS TO A WHITEFOOT PIPELINE, AND WHAT IS WORKAROUND

### 7.1 Ideas that exist only to work around constraints Snowghost does not have

| Mechanism | Why engines have it | Why Snowghost need not |
|---|---|---|
| Dirty bit propagation (`NeedsLayout`, `ChildNeedsStyleRecalc`) | mutable object graph; no key for "result is stale" | persistent results keyed by inputs; staleness = key mismatch |
| Change hints / `StyleDifference` property tables | one coarse key (whole ComputedStyle) | consumer-shaped key groups; reads rows checked by compiler |
| Style-sharing candidate checks | the true dependency set of matching is unavailable as data | explicit-input `match`/`cascade` + hash-consing |
| Relayout boundary heuristics, `contain` as optimization | cannot see which inputs the subtree read | boundary = key unchanged (still needed for *semantics* where CSS defines it) |
| `will-change`, layer hints | author must say which element will animate | the renderer owns animation descriptions [SG processes.md]; promotion is derived |
| Repaint boundaries (Flutter), canvases (Unity), `Volatile` (Slate) | raster cache granularity chosen by developer | paint results per fragment with ids; shell decides caches |
| Lifecycle barriers and `forced layout` | script can read layout synchronously mid-mutation; single main thread | N/A for stage dependencies; but synchronous layout *queries* from script remain a semantics issue to design |
| Tiles/layers (cc, WR) | raster surface cache + async scroll off main thread | shell concern (Skia); renderer exports ids/hashes |
| Flat display list + merge (Gecko) | raster API wants a linear command stream | tree of per-fragment nodes flattened at the shell boundary |

### 7.2 Ideas that transfer (ranked by my confidence they are right and useful)

1. **Result keyed by explicit inputs with immutable, position-free results** (LayoutNG, Q55). Established; matches the current design decision. Needs: stable node ids across edits, hash/eq on keys, arena for persistent results. [established]
2. **Consumer-shaped style groups and early cutoff at each stage boundary** (Stylo structs; Blink diff done by hand). A style recompute that yields equal values for a consumer's group must stop there. [established idea, new implementation]
3. **Static invalidation sets for selectors as reverse index** (Blink/Stylo). Established; implementation is a table + counted loops. [established]
4. **Separate geometry from content: property/spatial nodes vs primitives** (property trees, WebRender spatial tree, Masonry compose pass). Gives zero-repaint scroll/transform/opacity/position moves. [established]
5. **Stable primitive ids + content hashes in the display list for damage by id equality** (WebRender interning/tile descriptors). Promising: gives the Skia shell everything it needs for minimal raster without any tiling decision in the renderer. [promising]
6. **Summary trees for sequences** (Zed SumTree) as the structure for block-axis flow, line indexes and scroll extent. Promising but hard (margin collapsing and floats are not pure monoids). [promising/hard]
7. **Validity intervals instead of exact key equality** (generalization of NG's key coarsening). Not in any shipped engine to my knowledge. [uncertain, high upside for resize and viewport-dependent edits]
8. **Phase-of-read determines damage** (Compose). Transfers as "which stage reads this style group". [promising]
9. **Boundary derived from declared dependency** (Flutter `parentUsesSize`). Subsumed by (1): the key is the declaration.

### 7.3 Things no engine solves that the owner's ideal runs into (the honest limits)

- **Not everything is a DAG**: container queries and `:has()` create style-depends-on-layout / descendant-to-ancestor dependencies. Engines restrict them (containment requirements); a data-dependency pipeline must either restrict similarly or iterate to a fixpoint (cost, termination). [hard]
- **Real coupling is real**: width change => all text rebreaks; a change that moves a float re-flows later siblings; counters and nth-child are document-order chains; inherited properties flow downward over whole subtrees. "A style change affecting the whole page must redraw everything" (owner) is correct and engines do not beat it either; what matters is *no extra work beyond the true dependency set*.
- **Checking cost**: dependency-determined does not mean free: someone must enumerate the candidates. Push needs marking and a spine walk; pull needs visiting (O(visited)). Engines pay O(depth) + O(children per spine level). Making that O(changed) needs the summary-tree structures in 7.2(6) and per-parent child indexes; otherwise the floor is O(spine x width).
- **Key-compare overhead can exceed recompute for cheap nodes** (leaf text with short strings, empty boxes); engines cache at box granularity, not per text run, probably for this reason. [S] Grain for memoization is a design parameter, to be measured (E1/E2).
- **Parallelism changes the break-even**: with provable independence, recompute-from-scratch costs W/P + critical path; incremental costs D/P + check overhead + spine. For whole-document edits W/P can beat bookkeeping; for local edits D is tiny. [SG] The layout prototype ran html5 in 0.029 s at four workers (measured with fixed advances, not full layout) [SG layout DESIGN "What exists"], i.e. above a 16.7 ms frame even in parallel, so a full relayout cannot be the 60 fps path for such documents; incrementality is required for them, parallelism alone does not rescue it. Caveat: that prototype is simplified.

### 7.4 What the renderer must emit for a Skia-based shell (end of the transferable chain)

Per [SG processes.md] the shell owns raster, compositing, scrolling and compositor-only animation; the renderer ships display lists, layer trees and animation descriptions through shared memory. Implications from the engine survey:
- **Display structure as a tree of per-fragment nodes with stable ids and content hashes**, local-space geometry, referencing (transform, clip, effect, scroll) nodes by id (WebRender interning + property trees). The shell diffs by id/hash, not by list position.
- **Property node values updatable without touching the display structure** (scroll offsets, transform/opacity animations): the compositor-only fast path generalizes to anything whose key is only a property node.
- **Versioned delta format** (shared memory): "fragment ids replaced/removed/moved" rather than whole lists; or whole tree with structural sharing so the shell can pointer-compare subtrees. [S] The choice matters for cost of idle frames: engines (Blink) still pay O(items) on a no-op frame because of flat copying.
- **Damage as an optional shell computation** from ids; do not make the renderer compute rectangles unless needed for the shell's partial present.
- **Animation/transient inputs as explicit inputs**: the renderer should be able to answer "if only property node P changes, no recompute needed" by construction.

## 8. TREE OF OPEN QUESTIONS AND EXPERIMENTS

Everything here can be done with the existing full-recompute drivers on the three pages (ecma262, html5, apollo11); no incremental implementation needed for E1-E3, which is what makes them cheap discriminators.

### E1. Key-hit simulation (the decisive one)  -- settles: how much of the ideal is achievable with which key granularity
- **Method**: define a small corpus of mutation classes per page: (a) text edit in one paragraph (same line count / different line count), (b) toggle a class that changes `color` only, (c) change `width`/`display` of one block, (d) change `font-size` on one ancestor with 100/10k descendants, (e) insert a node at the start of a long sibling list, (f) viewport resize (width), (g) root font-size change, (h) change a custom property read by few vs many elements. For each: run the existing full style and layout before and after. Compute, per stage, (i) the *oracle minimal set* = nodes whose output differs between before and after; (ii) the set a key-equality scheme would recompute, for several key designs: whole-computed-style key vs consumer-group key; constraint-space key with exact equality vs with consumed-dimension coarsening; (iii) the extra visited-but-hit set (check cost).
- **Criterion recorded in advance**: a key design is "good enough" if recomputed/oracle <= ~3x on the local-edit classes and recomputed/total <= oracle-ish on global classes; and visited count is within an order of magnitude of recomputed. If whole-computed-style keys already meet that, group-split keys are unnecessary overhead (this would falsify my claim in 1.3).
- **Result decides**: key granularity (1.2/1.3), whether coarsening/validity intervals (2.1.3) matter, whether spine/wide-parent cost (2.4) dominates.

### E2. Wide-parent / spine cost
- Synthetic and real: parent with 1k/10k/100k children, change a child's height at position 0, middle, end. Measure re-place cost with (a) re-run loop with cache hits, (b) parallel scan, (c) summary tree (prototype in WF or even Python for op counts). Criterion: if (a) is under ~1 ms at 100k on 4 workers, defer summary trees.
- Also the real ecma262/html5 distribution: measure max sibling count and depth along the spine for random edits (cheap from the box tree).

### E3. Paragraph width equivalence classes (validity intervals)
- For every paragraph on the three pages, sweep available width in 1 px steps from min-content to max-content+; record the set of widths with identical break positions and heights. Report the fraction of widths in the largest equivalence interval and the number of distinct classes per paragraph. Also measure how much of a resize-by-delta (e.g. window dragged by 1-20 px) leaves each paragraph unchanged. Criterion: if more than ~half of paragraphs keep breaks across a 10 px resize, validity intervals pay off for resize; otherwise skip.
- Also cheap: for layouts where the paragraph's *height* is all that parents read, the key can be height rather than lines (early cutoff on the fragment's externally visible size: parent re-runs only if the child's size changed). Count how often a relayout of a child yields an equal size.

### E4. Display-structure and shell cost (needs a paint stage; later)
- Once a display list exists: compare (a) full redraw of the viewport from a retained tree on the Skia shell at 4K and 1080p, (b) damage by id/hash and partial redraw, (c) flat list vs tree emission cost for a no-op frame and a one-paragraph edit. Criterion: full redraw per frame well under the frame budget with cached per-fragment encodings and viewport culling => defer damage/tiles; measure power separately if relevant.
- Include the CPU-side cost to rebuild the visible-region display list for a scroll (which engines avoid by raster caching); that is the number that decides whether scroll must be shell-only.

### E5. Cross-stage barrier test (design, not measurement)
- Write down, for each of the E1 mutation classes, the dependency chain through style -> box tree -> layout -> paint -> property nodes, and mark which links are keyed by group, which by value early-cutoff, which by position/order. Any link that is "whole document" should have a named true dependency (document-order counter, viewport width) or be treated as a bug. This is the dependency audit that Blink/Gecko never did systematically; it is the owner's ideal made into a checklist. [S]

### Open questions
- Q-a: Is static `reads` granularity fine enough, or does the language need field-level reads (or sums over a style-group schema)? (E1)
- Q-b: Do synchronous layout queries from script (`offsetWidth`) make a persistent, demand-driven result tree necessary or contradictory? Not studied.
- Q-c: Hash-consing under parallel independence: concurrent interner vs two-phase intern; interacts with provable independence (Q47/Q53 decisions refuse shared caches [SG]). Needs a language/runtime answer.
- Q-d: Cycles (container queries, `:has()`): restrict like CSS (containment) or fixpoint?
- Q-e: How is a *sequence* represented so that edits are O(log N) and `--par` parallel scan is still available? Persistent B-tree/rope with summaries; Whitefoot support for such structures (arena-owned trees with provable disjoint writes) is unknown to me.
- Q-f: The Servo incremental work is recent and moving; check PRs #37751, #37849, #37866, #37957 and the later fragment-cache PRs for their *actual* cache key and invalidation rules before designing, they are the closest open-source analogue of what Snowghost is building (all [F titles/summaries only; I did not read the diffs]).

## 9. TOP THREE RECOMMENDATIONS

1. **Run E1 (key-hit simulation) with E3's width sweep before writing any incremental code.** It needs only the existing full-recompute drivers, costs days not weeks, and answers the three questions that shape everything else: what key granularity (whole style vs consumer groups; exact vs coarsened constraint space), whether early cutoff on external size (child size equal => parent skips) captures most of the win, and whether spine/width tax is real. It converts the owner's ideal into numbers per edit class and is the only item here whose outcome could change the design.
2. **Adopt LayoutNG's model deliberately and finish the job its authors could not**: results keyed by explicit inputs, immutable and position-free (already Q55/pipeline decision), stable node ids, and per-stage early cutoff; then have the compiler enforce key completeness, which Blink only enforces by convention. Concretely start with style -> layout at box/paragraph granularity within a BFC (not BFC granularity: Snowghost's own measurement shows one BFC holds 85-95% of text) with the constraint-space-equality key, and add key coarsening/validity intervals only where E1/E3 show misses.
3. **Fix the display-structure interface early, because it is the expensive thing to change later**: a tree of per-fragment paint nodes with stable ids and content hashes, local geometry, referencing property-tree node ids (transform/clip/effect/scroll), with property node values updatable without touching content (Chrome property trees + WebRender interning + Masonry compose). That lets the Skia shell do damage by id and caching by observed invalidation, keeps tiling/layering/damage out of the renderer, makes compositor-only changes the generic case (any change whose key is only a property node), and leaves "redraw the visible viewport every frame" as a valid fallback while the rest matures. Defer summary-tree sequences (2.4) until E2 shows a linear parent tax that matters.
