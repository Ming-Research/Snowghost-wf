# Architecture

Status: proposal under discussion with the owner. The decisions it proposes
are amendments in [`design/amendments/`](../../../design/amendments/) until
the owner rules on them. Everything else here is reasoning, estimates and
plans, not settled decisions.

## Question

What architecture lets a renderer written in Whitefoot keep every stage from
the document to the screen parallel and incremental, render the part of the
web platform that mainstream sites and generated applications use, and be
built by many agents working at once? What must Whitefoot provide for it?

## Scope

Snowghost serves two kinds of content with different compatibility needs:

- **Applications generated by AI coding tools.** The subset Snowghost
  supports can be written down and given to the agent that generates the
  application, so this content converges on what Snowghost implements. It is
  the first product.
- **Mainstream sites.** Their long tail of features never ends; they set the
  compatibility bar and the comparison workloads.

The subset is chosen from measured feature use, such as Chromium's
per-feature use counters and a crawl of target sites, not from the
specifications' tables of contents. Out of scope at first: video and audio,
WebGL and WebGPU, printing and paged media, vertical writing modes, and
complex-script shaping beyond what the first target content needs.

## Pipeline

### Units

The proposed unit of work is the independent formatting context: a block
formatting context root, a flex or grid item, an absolutely positioned box or
a table cell. It is the unit of four things at once:

- **storage**: its boxes and fragments are kept together;
- **parallel work**: once its constraints are known, it is laid out without
  reading any other unit's state;
- **invalidation**: a change inside it stops at its boundary when its outer
  size does not change;
- **caching**: its result is memoized by its inputs.

It is the finest boundary at which the CSS layout rules let a change stop.
Inside one block formatting context, floats, margin collapsing and line
breaking across inline boxes couple the elements, so a per-element unit would
not be independent.

### Local updates

Each stage processes only dirty paths:

- a change to one element's layout propagates upward to the first ancestor
  whose size does not change;
- the siblings after it are translated, not laid out again;
- every stage reuses the previous frame's results for unchanged subtrees by
  reference;
- frames are pipelined: script mutates the document for the next frame while
  the renderer works on a read-only snapshot of the last committed one.

### Where the standards serialize work

- **Inside one block formatting context**, floats, margin collapsing and
  inline line breaking are sequential. Parallelism comes from the number of
  independent contexts, so float-heavy documents are the worst case and flex
  and grid layouts the best.
- **Selectors** that depend on siblings or descendants (sibling combinators,
  `:nth-child`, `:has()`) and CSS counters couple elements in style.
- **Synchronous layout queries** from script, such as `offsetWidth` and
  `getBoundingClientRect`, cannot be deferred; they must be fast.
- **Paint order** within a stacking context is fixed by the standard.
- **Containing blocks** of absolutely and fixed positioned boxes can be
  distant ancestors, and transforms establish them too.
- **Container queries** make style depend on layout; containment breaks the
  cycle.
- **Fonts and images** arrive asynchronously and must invalidate only what
  they size.

### What Whitefoot contributes

1. **Complete cache keys.** A stage written as a `pure` Whitefoot function
   whose inputs are all parameters has a memoization key the compiler proves
   complete: a result that read something outside its key does not compile.
   Hand-maintained invalidation rules and caches can miss a dependency and
   render stale output.
2. **Subtree parallelism without locks.** If each unit's data occupies one
   contiguous region, recursion into children splits a range into disjoint
   windows, the form Whitefoot's parallel permission judgment already proves
   independent ([EFF-5 and OWN-7][spec]). The tree-shaped version is
   unverified; the first prototype checks it.
3. **One process.** Multi-process isolation in current engines assumes the
   renderer can be corrupted. A renderer proved memory safe can run in one
   process and save that memory, provided the script engine is memory safe
   too.

## Script

JavaScript runs on an interpreter written in Whitefoot, with no just-in-time
compiler (the `script` amendment):

- iOS does not let ordinary third-party applications generate executable
  code at run time, and an embedded just-in-time compiler is a security risk.
- A single-process renderer needs its script engine to be memory safe too.
- An exhaustive match over a closed sum type is Whitefoot's only dispatch, so
  bytecode dispatch is a match. Lowering a loop over that match to a chain of
  tail calls gives each instruction handler its own branch prediction and
  register allocation. The technique is Haberman's for protobuf parsing
  ([musttail interpreters][musttail]) and CPython 3.14's tail-calling
  interpreter ([What's new in Python 3.14][cpython]). Whitefoot today has a
  `musttail` marker for direct self calls only ([self-tail-calls][selftail]);
  the match lowering was designed earlier and not pursued (requirement W1).
- The engine needs a garbage-collected object heap written without unsafe
  code (requirement W5).
- test262 is the oracle, and its per-built-in organization divides the work.

## Workload

Order-of-magnitude estimates in Whitefoot lines for the scope above, refined
as modules are measured:

- networking (HTTP/1.1, HTTP/2, TLS 1.3, DNS, cookies, cache, gzip and
  brotli): 40,000 to 60,000;
- HTML parsing, the DOM and events: 30,000 to 50,000;
- CSS (parsing, selectors, cascade, about 200 properties, animations and
  transitions): 60,000 to 100,000;
- layout (block, inline, float, flex, grid, positioned, sticky, table,
  overflow, replaced elements, intrinsic sizing): 80,000 to 150,000;
- text (font parsing, WOFF2, shaping, bidirectional text, line breaking,
  fallback, rasterization, emoji): 50,000 to 100,000;
- images (PNG, JPEG, GIF, WebP) and an SVG subset: 30,000 to 60,000;
- paint, rasterization, compositing and scrolling: 50,000 to 100,000;
- the platform layer for three operating systems (windows, input, input
  methods, clipboard, GPU surfaces, basic accessibility): 30,000 to 60,000;
- web APIs (fetch, timers, animation frames, observers, storage, history,
  form controls, canvas 2D, workers, WebSocket, custom elements, shadow DOM):
  80,000 to 150,000;
- the JavaScript engine: 150,000 to 250,000.

The total is about 600,000 to 1,100,000 lines. The critical paths are the
JavaScript engine, the layout core and the platform layer.

## Division of work

Whitefoot's module design sets the division: the architect owns the module
graph and the `.wfm` interfaces, implementers write `.wf` bodies in parallel,
and a module's verdict depends only on its own files and its dependencies'
interfaces ([MOD-8][spec]; [architect and implementer workflow][modular]).

- **Implementer modules** are leaves with an oracle independent of
  Snowghost: the HTML tokenizer and tree builder (html5lib-tests), CSS syntax
  (css-parsing-tests), URL parsing (the web-platform-tests URL data), the
  Unicode bidirectional algorithm, line breaking and segmentation (the test
  files of UAX #9, #14 and #29), image decoders (PngSuite and each format's
  conformance images), brotli and WOFF2, HPACK, cryptographic primitives
  (NIST test vectors), number formatting, and JavaScript built-ins (test262).
- **The architect keeps the shared vocabulary and the skeleton**: node
  identity, geometry and fixed-point layout units, computed style, fragment
  trees, display lists and text runs; the incremental parallel scheduler,
  box-tree construction, block and inline layout, paint order, compositing,
  and the script object model and heap. They decide whether everything else
  can run in parallel and are the most expensive to change later.
- **Contracts carry the division.** The `requires`, `ensures` and effect rows
  of a `.wfm` are checked against every body, so an implementer's work is
  accepted against the architect's contract at the module check, not at
  integration.
- **The global oracle** is web-platform-tests filtered to the chosen subset;
  its pass rate is the progress measure.

## Whitefoot requirements

Each becomes a Whitefoot change through Whitefoot's own process when
Snowghost's work reaches it; `docs/todo.md` records each once it has a
minimal example.

- **W1. Match to tail-call chain lowering** for interpreter dispatch,
  designed in Whitefoot earlier and not pursued.
- **W2. Compiler throughput at this scale.** At the pinned `c84c4dd7a`, on a
  four-vCPU Intel Xeon 2.10 GHz container, `whitefootc --check` of
  `tests/programs/wfgrep.wf` (1,759 lines) took 2.40, 2.65 and 2.54 seconds
  in three runs, with a peak of 250 to 280 MB. At that rate, 600,000 lines
  checked on one thread take about 15 minutes. Modules check in parallel and
  incrementally, so this bounds only a cold build; the rate on large modular
  programs still needs measuring.
- **W3. A platform boundary**: windows, GPU surfaces, input and input
  methods, font enumeration, clipboard and accessibility on each operating
  system, as host modules in the trusted runtime. This enlarges the trusted
  base; its extent is the owner's decision.
- **W4. Concurrency**: tree-shaped dynamic parallelism, long-lived threads
  for the compositor, input and script, and read-only snapshots shared across
  frames and threads. Whether the current ownership model expresses the
  snapshots is unverified, and they are the foundation of the pipeline. This
  belongs with Whitefoot's I/O redesign.
- **W5. A garbage-collected object heap** without unsafe code, such as
  handles into arenas with a tracing collector, for script values.
- **W6. Vector code** for rasterization and decoding: measure whether
  automatic vectorization is enough.
- **W7. The impact report** of the modular design, which lists the
  implementation and caller tasks an interface edit creates. The compiler has
  the interface, module and composition checks but not this report, which is
  what dispatches work to implementers.

## First milestone (proposal)

Headless static rendering: an HTML and CSS subset rendered to pixels, with no
network, window or script. It is the earliest publishable result, tests the
pipeline thesis directly, avoids the three longest paths, and is the first
scale test of the compiler and of the architect and implementer workflow.

Comparisons with Chromium and Servo, each headless, on the same machine and
content:

1. first render of large static documents;
2. relayout of the whole page when the viewport width changes;
3. frame time after one element's layout property changes in a large page.

The owner sets the criteria before any measurement. Placeholders: on eight
cores, first render and full relayout at least three times faster than
Chromium, and a single-element change under 2 ms per frame.

## Agent writer trial (proposal)

Before modules are dispatched at scale, the same three tasks run with the
haiku, sonnet and opus models:

1. UAX #14 line breaking, judged by `LineBreakTest.txt`;
2. CSS syntax tokenizing and parsing, judged by css-parsing-tests;
3. PNG decoding, judged by PngSuite, with speed compared to libpng.

Each run records the oracle pass rate, whether Whitefoot accepts the program
with all its proofs, run time, elapsed time, turns and quota used, a
reviewer's assessment of the code, and the supervisor's interventions, keeping
apart the four observations of the investigation skill's agent writer trials.
The criterion that assigns a model to a class of task is written before the
runs. Whitefoot is in no model's training data, so how quickly each model
learns it from the specification, the patterns and the diagnostics is also
evidence for Whitefoot's design.

## Prior work

- Servo's style system, Stylo, computes styles in parallel with work
  stealing and was adopted into Firefox ([Inside a super fast CSS
  engine][stylo]).
- Ekioh's Flow lays out page elements concurrently on multiple threads
  ([Flow][flow]).
