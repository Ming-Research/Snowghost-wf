Decision: Layout stores an owned tree of formatting contexts, each holding its block boxes and paragraphs in flow order and owning its child contexts in `Box<Slots<Context>>`, with every paragraph broken into lines in one counted loop before the context's block pass places floats and breaks again only the paragraphs a float narrows, because the block pass is layout's only chain of true dependencies and a context's child contexts depend only on their element and width; in the prototype, with a fixed advance per character, no `clear` and floats that do not push each other, this made layout at four workers 3.31 and 2.94 times faster than the sequential build on html5 and apollo11, breaking again four paragraphs of apollo11 and none of html5 ([floats](../../research/investigations/concurrency/DESIGN.md#floats-speculative-line-breaking-and-fix-up)), instead of per-stage arrays indexed by element; provisionally for static rendering, since whether the context is also the unit of memoization and invalidation is decided by the first incremental prototype ([open question](../../research/investigations/concurrency/DESIGN.md#open-question-the-unit-of-storage-invalidation-and-caching)).

Decision: The box tree is built by one walk of the document in tree order that records each paragraph's text as pieces, byte spans of text nodes and single inserted scalar values, followed by one counted loop that decodes and collapses each paragraph's pieces into its text, because only the order of the flow is a chain while a paragraph's text depends on its own pieces alone, instead of decoding and collapsing text during the walk; measured, it made the builder and layout together 1.08 and 1.24 times faster at four workers on ecma262 and html5, short of the 1.5 sought, and the sequential build 34 and 21 percent slower, and it is kept because what the walk and the loop could still gain is under 1 percent of the four-worker pipeline ([box tree construction](../../research/investigations/concurrency/DESIGN.md#box-tree-construction)); provisionally, because two pages measured it, so it is measured again when the real box tree builder runs on more real pages.

Decision: A `font-family` list is matched against the installed faces through Snowghost's own table of the reference browser's resolution on its host: the generic families (serif to Liberation Serif, sans-serif to Liberation Sans, monospace to DejaVu Sans Mono, system-ui to DejaVu Sans), only the metric-compatible aliases (Arial and Helvetica, Times New Roman and Times, Courier New and Courier) and Liberation Serif for a list that matches nothing, with weight and style by CSS Fonts 4's matching and per-character fallback through the installed faces in a fixed order, because the reference draws all but about 0.1 percent of the measured pages' glyphs this way and refuses fontconfig's other substitutes ([fonts](../../research/investigations/layout/DESIGN.md#what-the-measured-pages-use)), instead of reading fontconfig's configuration, which would tie the renderer to one platform's font service.

Decision: Scrollbars take no space beside a scroll container or the viewport, because the reference renders with hidden scrollbars and overlay scrollbars behave so, instead of reserving 15 px beside every scroll container as desktop Chromium does by default.

Decision: Text is prepared in one counted loop over paragraphs, each iteration itemizing its own paragraph by font, script and style, shaping each item once with `pkg::font`, and finding its break opportunities and its min-content and max-content contributions, with font lists matched once per interned font group, because a paragraph's preparation depends on its own text and styles alone, instead of a shaping cache shared across paragraphs, which would order paragraphs that do not depend on each other; a line ending inside a shaped item keeps the item's advances without reshaping its edge, as `pkg::font` reports no unsafe-to-break positions, until a mismatch it causes is observed.

Decision: Each formatting context writes its boxes, line boxes and text fragments with offsets from its own border box, and its parent places it by one offset, with absolute positions computed only by the walk that dumps or paints, because a context's inside then depends on its available size alone, so sibling contexts lay out independently and moving a context touches none of its contents, instead of absolute positions written during layout, which need every ancestor placed first.

Decision: A context computes its min-content and max-content sizes when a parent's algorithm needs them (flex, grid, tables, floats and shrink-to-fit widths), its child contexts' in one counted loop, and keeps them, recursing one level per nested context rather than halving sibling runs, because they depend only on the context's subtree and most block-level contexts never read them, instead of one bottom-up pass over every context.

Decision: Tables follow the automatic and fixed table layout of CSS Tables 3's editor's draft, and where the draft leaves a step undefined, the reference browser's behavior, each such step recorded, because the draft is the specification the reference's table implementation follows, instead of CSS 2.2's informative automatic layout, which leaves column widths to the implementation.

Decision: A multi-column container is laid out as one column of its used column width, then its content is split into the fewest balanced columns between units no break may cross (each line of a paragraph, each row of a table child, each box whose `break-inside` avoids column breaks, each other child context), and a column map applied when boxes are placed moves each column's content beside the first, splitting a box that spans columns into one rectangle per column, because the measured pages break only there and the reference splits boxes so, while every unit keeps the layout it has in one column, so no context is laid out twice ([Q59](../../research/investigations/layout/DESIGN.md#owner-rulings)), instead of fragmenting during layout, which would lay out each column's content at a given height and thread a break position through every context kind; provisionally, until a page needs `column-span`, orphans and widows, or a break inside a box that is laid out differently in the next column.

Rejected:
- Leaving multi-column layout out of scope: rejected because 20.7 percent of html5's block boxes and 14 percent of apollo11's lie in multi-column containers, so the layout criterion could not hold on those pages ([Q59](../../research/investigations/layout/DESIGN.md#owner-rulings)).
- Decoding text during the walk: rejected because it keeps four fifths of the builder's work, turning text into scalar values, inside the walk's chain.
- A shaping cache shared across paragraphs, as Blink keeps per word: rejected because every paragraph would read and write it, ordering paragraphs that do not depend on each other; repeated words are shaped again, extra work off the critical path.
- Absolute positions written during layout: rejected because a context could not be laid out before all its ancestors were placed.
