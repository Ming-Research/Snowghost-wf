Decision: The style stage runs in three parts: one counted loop over the elements in document order matches each element and selects each longhand's winning declaration by a key of origin, importance, specificity and order, which needs no sorting; then a cascade level by level computes only what the parent decides, the font size, the custom properties and the inherited values, substituting `var()` in those: for each level of the element tree, one counted loop over the level's nodes that write nothing the levels share, then the level's other nodes in document order, and the pseudo-elements after the last level; then a second counted loop computes every value that is not inherited, each element substituting its own `var()` with no cache shared across elements and reading an ancestor's declarations again for an explicit `inherit` or a flex or grid parent, because matching and selecting the cascaded values depend only on the element and the rule store, only those three depend on the parent, a value that is not inherited still needs the element's own font size, which the pass decides, so no value is computed in the first loop, and a shared cache would order elements that do not depend on each other, so the only chain is the tree's depth, the parent-to-child dependencies, plus the few nodes that write the shared stores, while a duplicated substitution is extra work that does not lengthen that chain; among the three traversal shapes measured, matching in document order stores its results in the one order every consumer reads, while level order, within 5 percent of it, needs a second order map ([style measurement](../../research/investigations/concurrency/DESIGN.md#style-measurement)), instead of one sequential pass that cascades, computes and inherits everything, a cache of substituted values shared across elements, level-order storage or recursion that halves each sibling run; a level's elements lie scattered in document order, and Whitefoot's range facts and `apart` certificate prove the loop's writes through their indices disjoint, so the levels write straight into document order without a copy, and at four workers the pass ran 2.5 and 2.1 times faster on ecma262 and html5 ([level cascade](../../research/investigations/style/DESIGN.md#the-level-cascade)).

Decision: Matching tests an element only against the selector alternatives that its own id, class words and local name select through an index of each alternative's rightmost compound, plus the alternatives whose rightmost compound names none of them, each alternative tested alone, because an alternative whose rightmost compound names another id, class or type cannot match, so the matched rules are unchanged, while testing every rule cost about 590 tests per element ([rule index](../../research/investigations/concurrency/DESIGN.md#styles-work-per-element)) and indexing whole rules tested every alternative of a rule that one alternative selected: with the feature filter in both, per-alternative items made the sequential style stage 2.0, 1.8 and 1.4 times faster on apollo11, html5 and ecma262 ([matching](../../research/investigations/incremental-style/runs/matching.txt)), instead of testing every rule or indexing whole rules.

Decision: Before matching an alternative, a 256-bit Bloom filter of the element's own and its ancestors' ids, class words and local names rejects a rule when the filter lacks a feature that every alternative of the rule requires of the subject or, for a compound immediately followed by a descendant or child combinator, of an ancestor (a compound followed by a sibling combinator matches only a sibling and requires nothing); each element builds its filter by walking its own ancestors, because the filter only ever admits too much, so the matched rules are unchanged, and it halved a class edit's restyle on apollo11 (61 to 32 microseconds) and saves a third of apollo11's and html5's full style stage after per-alternative indexing ([matching](../../research/investigations/incremental-style/runs/matching.txt)), while a filter pushed and popped along a traversal would order each element after its parent, a dependency matching does not have, so the walk duplicates work instead; instead of walking ancestors for every descendant combinator, or a 1024-bit filter, which measured slower.

Decision: Matching reads each element's position among its siblings, and among its siblings of its type, and its class words, from one table built before matching (a class edit indexes its element's words again), because counting siblings at every `:nth-child` and `:nth-of-type` test cost time in proportion to the element's position, which made html5's four-worker style stage 4.1 times faster in one run while ecma262 ran 7 percent slower and apollo11 no faster, instead of counting at each test; the table is built by one sequential walk of the whole document, an order the counts do not need, so counting each parent's children in parallel, which also recounts only changed parents incrementally, is reopened when the walk's own cost is measured or incremental style needs it.

Decision: `ex` and `ch` are resolved from the x-height and the advance of the digit zero of the element's first available font, taken as the first generic family of its `font-family` list drawn with the environment's default font for that family, serif when the list has none, and given to the stage with the viewport, because the reference browser resolves them from those metrics and half an em, the fallback CSS allows, put 7.4 percent of ecma262's elements off in their right margin, by up to 15 percent ([ex and ch](../../research/investigations/style/DESIGN.md#choices-after-the-results)); provisionally, instead of half an em or matching named families against installed fonts, until the font stage matches families and loads web fonts, when the metrics come from the font each element actually uses.

Decision: The user-agent sheet gives the reference browser's computed values: it holds the HTML Standard's rendering rules where Chromium agrees with them and Chromium's own rules where the two differ, such as `table { border-color: gray }`, the form controls' fonts, borders and padding, no `line-height: normal` on `sub` and `sup` and no `counter-reset: list-item` on lists, which Chromium resets implicitly, because the renderer follows Chromium where it and a specification differ ([pipeline](../pipeline.md)), instead of following the Standard's sheet and recording where Chromium differs ([style results](../../research/investigations/style/DESIGN.md#choices-after-the-results)).

Decision: The first part also matches the rules whose subject ends in `::before` or `::after`, and the stage computes each generated box's style with its element as parent into a sparse list in document order beside the elements' styles, because a generated box depends only on its element's matched rules and computed style, so it joins the same loops, while most elements generate none ([interface choices](../../research/investigations/layout/DESIGN.md#interface-choices)), instead of a pseudo-element slot for every element or generated boxes interleaved into the element index that the oracle and every consumer read.

Decision: The style stage keeps its state across edits: each group's table keeps its identifiers and an edit's restyled nodes look their values up and append the ones not found, the custom-property sets, list values and generated text are interned the same way, and layout's keys therefore stay valid across a restyle without the whole-page delta; because an edit then waits only on its own misses, where per-run tables made every edit intern and compare the whole page ([Q89](../../research/investigations/incremental-style/DESIGN.md#decisions)), instead of per-run tables mapped by value (Q83, which held while every edit reran the whole stage) or identifiers by content hash, whose collisions no proof rules out.

Decision: The kept state's rows are stable slots: an element's slot is its preorder position at the last full build, an insertion appends rows for its elements and their styled nodes, a removal leaves holes the passes skip, and an edit takes the new elements' depths from their parents instead of building the traversal again, because an insertion then moves no existing row, so the full build keeps its order, its output and its parallel loops, the NodeId-to-slot map is the traversal's existing order map, and a block edit's style work follows the set it restyles, 91 to 389 microseconds sequentially against 119 to 958 ms for the rebuilt stage on the three pages ([Q108 and Q111](../../research/investigations/structure-edits/DESIGN.md#decisions), [slots](../../research/investigations/structure-edits/runs/slots.txt)), instead of rows indexed by NodeId, which hold a row for every text node (2.3 times the elements on ecma262) and grow with the DOM's node array, which cannot be compacted alone, or preorder rows that every insertion shifts; slots only grow until the next full build, and their compaction is recorded in the TODO.

Decision: A class edit's restyle set comes from a reverse index of the rules' class features, built with the rules, naming for each class the elements a change can reach (the element itself, its descendants, its later siblings and their descendants, carrying the rule's subject key); the set is rematched and the level cascade continues to a child only while what it inherits, or its own style, changed, because those are exactly the elements whose winners or inherited inputs can change ([Q91](../../research/investigations/incremental-style/DESIGN.md#decisions), [step 3](../../research/investigations/incremental-style/runs/step3.txt)), instead of rematching the edited element's subtree, which for a class on body rematches the page; an edit whose reach the index cannot bound, or that changes which pseudo-elements an element has, rebuilds without changing the result.

Decision: An insertion or removal of a child under a parent rematches, besides the inserted subtree, the elements a structural reverse index names: each position pseudo-class, sibling combinator and `:empty` records, with its rule's subject key, which of the parent's remaining children it can reach by their place around the edit point (the element right before or after it, or every element before or after: `+` and `:first-child` the next, `:last-child` the previous, `~`, `:nth-child` and `:first-of-type` every later one) and the ancestor features its left compounds require of the parent or its ancestors, and the set walks only those places from the point outward, because an insertion changes a remaining child's match only through its neighbours or its counted position, and a rule whose ancestors the parent's chain lacks cannot match there ([Q110 and Q113](../../research/investigations/structure-edits/DESIGN.md#decisions), [structure check](../../research/investigations/structure-edits/runs/structure-check.txt)), instead of rematching the parent's children and their subtrees, which on html5 named 58,230 elements for an insertion that changed none, against 548 with sides and context.

Decision: The style stage hands layout a sparse list of the elements whose computed style changed in what layout reads, each marking layout through the uses its boxes recorded, and says separately whether an input of box construction changed, because marking then costs the changed elements and their context paths ([Q93](../../research/investigations/incremental-style/DESIGN.md#decisions)), instead of a flag per element with whole-tree validation and marking, two page-sized walks per edit.

Decision: Style attribute and presentational hint declarations are parsed once at load and found by the element's NodeId through a dense index, because an insertion or removal leaves each element's NodeId and so its declarations in place, instead of preorder positions, which an insertion shifts so that every later record lands on the wrong element, or parsing them again after every edit ([Q85](../../research/investigations/incremental-layout/DESIGN.md#decisions)).

Decision: Provisionally, a root font-size change restyles the elements whose winning declarations can read the root's size (a rem length, a var() value whose text or some custom property's value holds rem, a track list or border spacing) through the level cascade, and rebuilds without matching only when they or the visited elements pass a sixty-fourth of the elements, because only those elements and the inherited font chain read the root's size, which took ecma262's root font-size edit from 989 to 14 ms after the rebuild had stopped matching (E1 measured 1,426 ms before either), while on a page whose every element inherits the root's size the bulk passes are cheaper than the levels ([root font](../../research/investigations/incremental-style/runs/rootfont.txt)), instead of rebuilding every node on every root font-size change.

Rejected:
- Per-run interning tables mapped by value between runs (Q83): rejected because once a restyle covers only the elements an edit reaches, interning and comparing the whole page on every edit is the dominant cost and an order the restyle does not need ([Q89](../../research/investigations/incremental-style/DESIGN.md#decisions)); it was the decided design while every edit reran the whole stage.
- The HTML Standard's sheet, recording where Chromium differs rather than copying it: rejected because readers judge a renderer against Chromium, and the Standard's rules alone left table borders, sub and sup line heights (4.5 percent of ecma262's block boxes moved) and form controls different from it; it was the decided sheet until the layout stage measured that cost.
- A cache of `var()` substitutions shared across elements: rejected because every element would read and write it, ordering elements that do not depend on each other, so the cascade could never run in parallel.
- One pass in document order that cascades, computes and inherits everything: rejected because only the font size, the custom properties and the inherited values depend on the parent, and the rest of the work in that pass lengthens the one sequential chain.
- Level-order storage, one counted loop per tree level: rejected because it needs a second order map for every consumer that reads styles in document order, while it came only within 5 percent of matching in document order at four workers.
- Recursion that halves each sibling run in document order: rejected because the runtime's fixed recursion budget runs out under the wide sibling runs of real pages, giving apollo11 a four-worker speedup of 1.11 against 3.62, though it led on the synthetic pages; reopened if Whitefoot's recursion budget follows unbalanced trees, the gap reported to Whitefoot.
- Cascading per formatting context: rejected because the pipeline keeps no unit of parallel work and an element's cascade depends on its parent, not on its formatting context; not measured.
- One pass in document order for what the parent decides: rejected because it orders siblings that depend only on their common parent, a chain as long as the document, where the levels make it the tree's depth; it was the decided pass until Whitefoot could prove writes through a level's scattered indices disjoint.
- Every node of a level in one loop, with the shared stores behind a lock or merged after each level: rejected because it orders the few nodes that write those stores against all the others, and Whitefoot has no lock a counted loop may take.
