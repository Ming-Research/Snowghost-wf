Decision: The style stage runs in three parts: one counted loop over the elements in document order matches each element and selects each longhand's winning declaration by a key of origin, importance, specificity and order, which needs no sorting; then a cascade level by level computes only what the parent decides, the font size, the custom properties and the inherited values, substituting `var()` in those: for each level of the element tree from the root, one counted loop over the level's nodes that write nothing the levels share, then the level's nodes that declare custom properties or keep a pending value in the stage's side tables, in document order, and the pseudo-elements in one loop after the last level; then a second counted loop computes every value that is not inherited, each element substituting its own `var()` with no cache shared across elements and reading an ancestor's declarations again for an explicit `inherit` or a flex or grid parent, because matching and selecting the cascaded values depend only on the element and the rule store, only those three depend on the parent, a value that is not inherited still needs the element's own font size, which the pass decides, so no value is computed in the first loop, and a shared cache would order elements that do not depend on each other, so the only chain is the tree's depth, the parent-to-child dependencies, plus the few nodes that write the shared stores, while a duplicated substitution is extra work that does not lengthen that chain; among the three traversal shapes measured, matching in document order stores its results in the one order every consumer reads, while level order, within 5 percent of it, needs a second order map ([style measurement](../../research/investigations/concurrency/DESIGN.md#style-measurement)), instead of one sequential pass that cascades, computes and inherits everything, a cache of substituted values shared across elements, level-order storage or recursion that halves each sibling run; a level's elements lie scattered in document order, and Whitefoot's range facts and `apart` certificate prove the loop's writes through their indices disjoint, so the levels write straight into document order without a copy; at four workers the pass became 2.49 and 2.06 times faster on ecma262 and html5 and the whole stage 15 percent faster on ecma262 and no slower elsewhere, while the sequential build pays for the levels ([level cascade](../../research/investigations/style/DESIGN.md#the-level-cascade)).

Decision: Matching tests an element only against the rules that its own id, class words and local name select through an index of each rule's rightmost compound, plus the rules whose rightmost compound names none of them, because a rule whose rightmost compound names another id, class or type cannot match, so the matched rules are unchanged, while testing every rule cost about 590 tests per element; in one run it made the four-worker style stage 3.2, 1.3 and 2.1 times faster on ecma262, html5 and apollo11 ([rule index](../../research/investigations/concurrency/DESIGN.md#styles-work-per-element)), instead of testing every rule against every element.

Decision: Matching reads each element's position among its siblings, and among its siblings of its type, from one table built before matching, because counting siblings at every `:nth-child` and `:nth-of-type` test cost time in proportion to the element's position, which made html5's four-worker style stage 4.1 times faster in one run while ecma262 ran 7 percent slower and apollo11 no faster, instead of counting at each test; the table is built by one sequential walk of the whole document, an order the counts do not need, so counting each parent's children in parallel, which also recounts only changed parents incrementally, is reopened when the walk's own cost is measured or incremental style needs it.

Decision: `ex` and `ch` are resolved from the x-height and the advance of the digit zero of the element's first available font, taken as the first generic family of its `font-family` list drawn with the environment's default font for that family, serif when the list has none, and given to the stage with the viewport, because the reference browser resolves them from those metrics and half an em, the fallback CSS allows, put 7.4 percent of ecma262's elements off in their right margin, by up to 15 percent ([ex and ch](../../research/investigations/style/DESIGN.md#choices-after-the-results)); provisionally, instead of half an em or matching named families against installed fonts, until the font stage matches families and loads web fonts, when the metrics come from the font each element actually uses.

Decision: The user-agent sheet gives the reference browser's computed values: it holds the HTML Standard's rendering rules where Chromium agrees with them and Chromium's own rules where the two differ, such as `table { border-color: gray }`, the form controls' fonts, borders and padding, no `line-height: normal` on `sub` and `sup` and no `counter-reset: list-item` on lists, which Chromium resets implicitly, because the renderer follows Chromium where it and a specification differ ([pipeline](../pipeline.md)), instead of following the Standard's sheet and recording where Chromium differs ([style results](../../research/investigations/style/DESIGN.md#choices-after-the-results)).

Decision: The first part also matches the rules whose subject ends in `::before` or `::after`, and the stage computes each generated box's style with its element as parent into a sparse list in document order beside the elements' styles, because a generated box depends only on its element's matched rules and computed style, so it joins the same loops, while most elements generate none ([interface choices](../../research/investigations/layout/DESIGN.md#interface-choices)), instead of a pseudo-element slot for every element or generated boxes interleaved into the element index that the oracle and every consumer read.

Rejected:
- The HTML Standard's sheet, recording where Chromium differs rather than copying it: rejected because readers judge a renderer against Chromium, and the Standard's rules alone left table borders, sub and sup line heights (4.5 percent of ecma262's block boxes moved) and form controls different from it; it was the decided sheet until the layout stage measured that cost.
- A cache of `var()` substitutions shared across elements: rejected because every element would read and write it, ordering elements that do not depend on each other, so the cascade could never run in parallel.
- One pass in document order that cascades, computes and inherits everything: rejected because only the font size, the custom properties and the inherited values depend on the parent, and the rest of the work in that pass lengthens the one sequential chain.
- Level-order storage, one counted loop per tree level: rejected because it needs a second order map for every consumer that reads styles in document order, while it came only within 5 percent of matching in document order at four workers.
- Recursion that halves each sibling run in document order: rejected because the runtime's fixed recursion budget runs out under the wide sibling runs of real pages, giving apollo11 a four-worker speedup of 1.11 against 3.62, though it led on the synthetic pages; reopened if Whitefoot's recursion budget follows unbalanced trees, the gap reported to Whitefoot.
- Cascading per formatting context: rejected because the pipeline keeps no unit of parallel work and an element's cascade depends on its parent, not on its formatting context; not measured.
- One pass in document order for what the parent decides: rejected because it orders siblings that depend only on their common parent, a chain as long as the document, where the levels make it the tree's depth; it was the decided pass until Whitefoot could prove writes through a level's scattered indices disjoint.
