Decision: Snowghost runs as two processes, a renderer written in Whitefoot and a shell written in Rust, connected by data rather than calls: the renderer sends display lists, property trees and animation descriptions in a versioned format through shared memory and receives input and loaded resources over a channel, because a data boundary keeps the threading constraints of the shell's libraries out of the renderer, lets each shell component be replaced later without changing the renderer, and keeps unproved code in its own process, instead of linking those libraries into the renderer as trusted host code.

Decision: The renderer owns the document, style, layout including text shaping, paint, script, image decoding and font validation, because these carry the pipeline's parallel and incremental work and parse the page's untrusted content, which Whitefoot proves memory safe, instead of handing page content such as images and fonts to the shell's libraries.

Decision: The shell owns windows, input and input methods, accessibility, the clipboard, system fonts, rasterization, compositing, presentation, scrolling, compositor-only animations, networking and storage, built first on existing libraries such as Skia for rasterization and compositing, because rasterization and compositing belong on the GPU and those libraries hold years of optimization that would be too costly to rebuild, instead of writing rasterization and compositing in Whitefoot first.

Decision: The renderer sends the shell facts about the page and the shell owns every policy that turns them into pixels: the renderer states each display chunk's stable identity, content hash and bounds including effect outsets, the transform, scroll, clip and effect nodes it hangs from, paint order, opaque areas, what reads its backdrop, which property nodes animate and how, and per change whether a chunk changed in content or only in geometry, while the shell decides per platform and by measured cost how to draw, which pixels to cache, how to scroll and how to present, and every combination of its policies must produce the pixels a full redraw of the scene produces, because platforms differ in what their compositors and presentation interfaces allow, so these choices are measured and changed in the shell without touching the renderer or risking a wrong pixel (Q65, [research](../research/investigations/incremental/DESIGN.md#6-the-paint-boundary)), instead of the renderer grouping content into compositing layers from hints such as `will-change` and overlap, which decides platform policy in paint.
