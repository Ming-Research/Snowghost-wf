Decision: The Snowghost engine binary stays within 10 000 000 bytes, a hard limit that `make check` enforces on every push and that only the owner changes, because the owner set it as 10 MB and the decimal reading is the stricter, 4.6 percent below 10 MiB (10 485 760 bytes), while the largest build measured uses 44.8 percent of it ([results](../../research/investigations/binary-size/README.md#results)), so the stricter reading costs no work today, instead of 10 MiB.

Decision: While the first release, a typesetting engine of style and layout, has no shell, the limit covers the renderer binary alone, and the shell joins the measured size when a release ships one, because the check can measure only a binary that exists and the shell's Rust libraries, Skia among them, are a separate program ([processes](../processes.md)), instead of counting a shell by estimate.

Decision: The size is judged on the Linux x86-64 build, as linked and unstripped, because the Linux build is 1.91 times the macOS build (4 475 416 against 2 338 968 bytes), so a limit met there is met on macOS, and stripping saves 10.7 percent on Linux and 1.5 percent on macOS while needing a step the build does not otherwise have ([results](../../research/investigations/binary-size/README.md#results)), instead of judging the macOS arm64 build or the stripped binary.

Decision: Until an engine binary exists, the check measures `layout_oracle`, the driver of the whole page pipeline, built with `--par`, because it is the largest build of the pipeline measured, 4 475 416 bytes on Linux against 2 975 160 for its sequential build (`--par` adds 50 percent) and 3 169 576 for the next largest driver, so a limit it meets is met by every other measured build of the same code ([results](../../research/investigations/binary-size/README.md#results)), instead of a sequential build or a smaller driver; provisionally, since the stages still to be written add code and the margin at the first engine binary is unknown, and the check measures the engine binary itself once one exists.

Rejected:
- Counting a shell estimate toward the first release's limit: rejected because the first release has no shell, so the estimate would be a number no build can confirm or contradict, and the check would pass or fail on a guess ([choices](../../research/investigations/binary-size/README.md#choices)).
- 10 MiB as the limit: rejected because it passes a binary between 10 000 000 and 10 485 760 bytes that the owner's decimal 10 MB reading refuses, while the stricter reading costs nothing now, the largest build being 44.8 percent of it.
- Judging the macOS arm64 build or each platform separately: rejected because a macOS-only gate would pass a Linux build up to 1.91 times larger than the limit allows, and a gate per platform adds no check while Linux is the larger on every driver measured; reopen it if a measured build on another platform exceeds Linux's ([results](../../research/investigations/binary-size/README.md#results)).
- Judging the stripped binary: rejected because it would hide 10.7 percent of the Linux build from the check behind a step the build does not run, and the margin does not need that room.
- A sequential build or a smaller driver as the stand-in: rejected because the sequential build is a third smaller than the parallel one on Linux and every other driver is smaller still, so either could pass while the parallel pipeline build fails ([results](../../research/investigations/binary-size/README.md#results)).
